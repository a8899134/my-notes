## 一、锁和隔离级别的作用
### 1.1 一个场景引出问题
假设你经营的电商网站，同一时刻有两个用户在做操作：
1. 时间 10:00:00，用户 A 查询“手机”类商品的库存，发现剩 10 件
2. 时间 10:00:01，用户 B 下单买了一部手机，将库存从 10 改为 9，提交事务
3. 时间 10:00:02，用户 A 基于刚才查到的 10 件做库存预警决策，但实际库存已是 9 件

如果数据库不加以控制，用户A可能会基于“10件”这个过时信息做决策，导致超卖。更严重的情况是：两个事务同时修改同一条数据，后提交的覆盖了先提交的—这叫更新丢失(Lost Update)。

数据库的锁机制和事务隔离级别，就是用来解决这类并发问题的两套工具：

|工具|核心作用|通俗比喻|
|---|---|---|
|锁(Lock)|控制多个事务同时操作同一数据时的访问权限|厕所的“有人/无人”门锁|
|事务隔离级别(Isolation Level)|定义事务之间相互隔离的程度，决定“能看到多少别人的改动”|厕所隔间的门缝有多大—是全封闭、半透明，还是根本没门|

两者相辅相成：隔离级别定义了“规则”，锁是实现这些规则的具体“手段”。

事务并发产生三个问题 → 隔离级别定义规则(允许什么、禁止什么)→ MVCC 负责读(快照读，解决脏读和不可重复读)→ 锁负责写和幻读(记录锁、间隙锁)。

## 二、并发事务三大问题
在讲锁和隔离级别之前，必须先搞清楚它们要解决什么问题。
### 2.1 脏读
脏读全称叫 Dirty Read

定义：一个事务读到了另一个未提交事务修改过的数据。

发生期间：发生在 Redo Log 处于 prepare、Binlog 还没写、事务还在“悬着”的时候。RC/RR 靠 Undo Log 读取旧值来防住它。

解决方式: 靠 MVCC(快照)，不是靠锁，

### 2.2 不可重复读
不可重复读全称叫Non-Repeatable Read

定义：在同一事务中，两次读取同一条记录，结果不一致(中途被其他已提交事务修改了)。

发生期间：发生在写事务提交(COMMIT)之后，但读事务自身还未结束之前。

解决方式: 靠 MVCC(快照)，不是靠锁
### 2.3 幻读
幻读全程叫 Phantom Read。
定义：在同一事务中，两次执行同一条范围查询，返回的记录条数不一致(中途有其他事务插入或删除了符合条件的记录)。

发生期间：发生在写事务提交(COMMIT)之后，但读事务自身还未结束之前。

解决方式: 靠 锁(间隙锁 Gap Lock)，这才是锁上场的地方。

### 2.4 解决方法

| 脏读    | RU 下发生           | 读到未提交的数据  | 升级到 RC           |
| ----- | ---------------- | --------- | ---------------- |
| 不可重复读 | RC 下发生           | 同一条记录内容变了 | 升级到 RR           |
| 幻读    | RR 下可能发生(RC 也可能) | 记录条数变了    | 升级到 S，或 RR 下用间隙锁 |

## 三、事务隔离级别
SQL 标准定义了四种事务隔离级别，MySQL InnoDB 全部支持。

| 隔离级别     | 脏读   | 不可重复读 | 幻读     | 并发性能 | 典型应用场景        |
| -------- | ---- | ----- | ------ | ---- | ------------- |
| 读未提交(RU) | ✅ 可能 | ✅ 可能  | ✅ 可能   | 最高   | 极少使用，一致性要求极低  |
| 读已提交(RC) | ❌ 不会 | ✅ 可能  | ✅ 可能   | 较高   | 互联网多数 OLTP 默认 |
| 可重复读(RR) | ❌ 不会 | ❌ 不会  | ✅ 基本避免 | 中等   | MySQL 默认级别    |
| 串行化(S)   | ❌ 不会 | ❌ 不会  | ❌ 不会   | 最低   | 强一致性场景，极少使用   |
```
数据存储位置：
┌─────────────┐
│ Buffer Pool │  ← 当前最新值(可能已提交，也可能未提交)
│   (内存)   │
├─────────────┤
│  Undo Log   │  ← 历史旧值链(被修改前的版本)
│   (硬盘)   │
└─────────────┘

Read View：事务第一次查询时拍的照片，记录当时"哪些事务还没提交"
```
### 3.1 读未提交(RU)
读未提交全称叫 READ UNCOMMITTED，缩写 RU
行为：一个事务可以读取到其他事务尚未提交的修改。

数据来源：读的是 Buffer Pool(内存) 里已经修改好的那个数据(比如 80)，此时数据还没提交。

锁机制：几乎不加锁，只有写操作加行级排他锁。

问题：会出现脏读、不可重复读、幻读全部三个问题。

使用建议：生产环境几乎从不使用。仅在极少数“对数据一致性完全不在乎、只追求极致性能”的场景下考虑。

```
SELECT balance FROM accounts WHERE id = 1
         │
         ▼
   直接去 Buffer Pool 读
         │
         ▼
   不管有没有提交，直接返回当前值

```
### 3.2 读已提交(RC)
读已提交全称叫 READ COMMITTED，缩写 RC
行为： 一个事务只能读取到其他事务已经提交的修改。未提交的事务修改对它不可见。
数据来源： 已提交事务写入 Buffer Pool 的数据”或“Undo Log 中的旧数据”。

锁机制：
- 只有记录锁(Record Lock)
- 没有间隙锁(Gap Lock)，临键锁退化为记录锁
- 语句执行完会释放不匹配行的锁

解决的问题： 解决了脏读问题。查询发现数据正在被修改(未提交)，会绕道去 Undo Log 读旧值，不用锁去等。

未解决的问题： 不可重复读、幻读仍然会发生。

使用建议： 互联网公司的首选隔离级别。因为没有间隙锁，锁范围更小，并发性能更高，死锁风险更低。
```
SELECT balance FROM accounts WHERE id = 1
         │
         ▼
   去 Buffer Pool 找到这行数据(当前值 = 180)
         │
         ▼
   检查这个修改的【事务 ID】是否已经提交？
         │
    ┌────┴────┐
    │         │
  已提交     未提交
    │         │
    ▼         ▼
 返回 180   去 Undo Log 读旧值 200
             │
             ▼
           返回 200
```
### 3.3 可重复读(RR)
可重复读全称叫 REPEATABLE READ，缩写 RR

行为： 同一个事务里，第一次查询某条数据之后，不管别的事务在这期间怎么改、怎么提交，你后续再查这条数据，结果永远和第一次查到的一模一样。

数据来源： 来源于事务第一次查询时生成的一个 “快照(Read View)，如果快照里没有(比如第一次查的时候还没这条数据)，就顺着指针去 Undo Log 里找历史版本 。

锁机制：
- 记录锁 + 间隙锁 + 临键锁完整生效
- 锁持续到事务结束
解决的问题： 脏读、不可重复读。脏读和不可重复读都是靠“Read View 固定不变”解决的。

未解决的问题：幻读仍然会发生。

幻读的处理：InnoDB 通过临键锁(Next-Key Lock) 在 RR 下基本解决了幻读。

⚠️ 注意：
虽然 SQL 标准说 RR 级别下幻读“可能”发生，但 MySQL InnoDB 的 RR 通过临键锁实际上阻止了幻读。

使用建议： MySQL 的默认隔离级别，适合对数据一致性要求较高的业务。
```
第一次 SELECT：
         │
         ▼
   生成 Read View(拍一张照片)
   记录：当前有哪些事务未提交
         │
         ▼
   去 Buffer Pool 找值
         │
         ▼
   检查该行的事务 ID 在照片里吗？
         │
    ┌────┴────┐
    │         │
  在照片里    不在照片里
(未提交)    (已提交)
    │         │
    ▼         ▼
 去 Undo Log  直接返回
 找旧版本     当前值
 直到找到
 不在照片里
 的版本

后续 SELECT：
         │
         ▼
   直接复用第一次的照片
   (不重新拍)
         │
         ▼
   按照同一张照片判断是否可见
```
### 3.4 串行化(S)
串行化全称叫 SERIALIZABLE 缩写 S

行为： 所有事务串行执行，一个事务执行完，下一个才能开始。

锁机制：
- 所有查询自动加共享锁(S 锁)
- 所有写操作自动加排他锁(X 锁)
- 相当于表级锁控制

解决的问题： 脏读、不可重复读、幻读全部解决。

使用建议： 生产环境几乎从不使用。并发性能极差，仅在极少数“宁可牺牲性能也要绝对一致”的特殊场景使用。
### 3.5 MySQL 隔离级别相关命令
查看当前隔离级别：
```
-- 查看当前会话的隔离级别(MySQL 8.0)
SELECT @@transaction_isolation;

-- 查看全局隔离级别
SELECT @@global.transaction_isolation;

-- MySQL 5.7 使用以下命令
SELECT @@tx_isolation;
```
设置隔离级别：
```
-- 设置当前会话的隔离级别为“读已提交”
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;


-- 设置全局隔离级别(新连接生效)
SET GLOBAL TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 设置下一个事务的隔离级别
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

## 四、MVCC 机制
### 4.1 什么是 MVCC
MVCC(Multi-Version Concurrency Control，多版本并发控制) 是 InnoDB 实现高性能并发读写的核心技术。

核心思想：写操作创建新版本，读操作读取旧版本，从而实现读不阻塞写、写不阻塞读。

💡 通俗理解：就像 Git 的版本管理—每个人修改代码时都创建新版本，其他人可以随时查看历史版本，互不干扰。
### 4.2 MVCC 依赖的基础
MVCC 依赖 Undo Log 日志。
InnoDB 中，每行记录有两个隐藏字段：
1. trx_id，最后一次修改该记录的事务 ID
2. roll_pointer，指向 Undo Log 中该记录的上一个版本
同一条记录的多次修改，通过 roll_pointer 串成一个版本链。当需要读取历史版本时，沿着版本链找到对应的 Undo Log 记录即可。
### 4.3 快照读 vs 当前读
MVCC 将读操作分为两种：

| 读类型                | 读取内容                    | 是否加锁  | 示例                                  |
| ------------------ | ----------------------- | --------- | ----------------------------------- |
| 快照读(Snapshot Read) | 事务开始时的历史版本(通过 Undo Log) | ❌ 不加锁 | 普通 SELECT                           |
| 当前读(Current Read)  | 数据库中的最新版本               | ✅ 加锁  | SELECT ... FOR UPDATE、UPDATE、DELETE |

快照读是 MVCC 的精髓—普通的 SELECT 查询不需要加任何锁，直接读取历史快照，性能极高。

当前读则退化为基于锁的并发控制，必须加锁才能保证数据一致性。

### 4.4 Read View(读视图)
MVCC 通过 Read View 来决定一个事务能看到哪些数据版本。
Read View 的构成：

|字段|含义|
|---|---|
| mids |创建 Read View 时，所有活跃事务(未提交)的事务 ID 列表|
| mintrxid | mids 中的最小事务 ID|
| maxtrxid |下一个将要分配的事务 ID|
| creatortrxid |创建该 Read View 的事务 ID|

可见性判断规则：
- 如果某条记录的 trxid < mintrx_id：说明该记录在 Read View 创建之前已提交，可见
- 如果某条记录的 trxid > maxtrx_id：说明该记录在 Read View 创建之后才产生，不可见
- 如果 mintrxid ≤ trxid ≤ maxtrxid：需要检查 trxid 是否在 m_ids 中
    - 在 m_ids 中(未提交)：不可见，去 Undo Log 找更旧的版本
    - 不在 m_ids 中(已提交)：可见
### 4.5 RC 与 RR 下 Read View 的区别
| 隔离级别     | Read View 创建时机                      | 效果                              |
| -------- | ----------------------------------- | ------------------------------- |
| RC(读已提交) | 每条 SELECT 语句都重新生成一个新的 Read View     | 每次查询都能看到其他事务最新已提交的数据 → 会出现不可重复读 |
| RR(可重复读) | 事务启动时只生成一次 Read View，后续所有 SELECT 共用 | 整个事务期间看到的数据始终一致 → 解决了不可重复读


## 五、MySQL 锁的类型
MySQL 的锁可以从多个维度分类。下面按照锁的粒度从大到小逐一讲解。
### 5.1 全局锁(Global Lock)
核心作用：对整个数据库实例加锁，使整个库处于只读状态。

典型场景：全库逻辑备份(mysqldump)时，为了保证备份数据的一致性，需要确保备份期间没有数据写入。

命令：
```
-- 加全局读锁(整个库只读)
FLUSH TABLES WITH READ LOCK;

-- 解锁
UNLOCK TABLES;
```
风险：全局锁会阻塞所有写操作(INSERT、UPDATE、DELETE、DDL)，对业务影响极大。

生产环境建议用 mysqldump --single-transaction 配合 MVCC 来做一致性备份，避免加全局锁。

### 5.2 表级锁(Table Lock)
表级锁是 MySQL 中粒度较大的锁，锁定整张表。
#### 5.2.1 表锁的两种模式
| 锁类型            | 说明                 | 其他事务可读？ | 其他事务可写？ |
| -------------- | ------------------ | ------- | ------- |
| 读锁(READ Lock)  | 共享锁，允许其他事务读取，但禁止写入 | ✅ 可以    | ❌ 阻塞    |
| 写锁(WRITE Lock) | 排他锁，禁止其他事务读写       | ❌ 阻塞    | ❌ 阻塞    |

命令：
```
-- 手动加读锁
LOCK TABLES users READ;

-- 手动加写锁
LOCK TABLES users WRITE;

-- 查看当前哪些表被锁定
SHOW OPEN TABLES WHERE In_use > 0;

-- 解锁(释放当前会话的所有表锁)
UNLOCK TABLES;
```
特点：
- 优点：开销小，加锁快，不会出现死锁
- 缺点：锁定粒度大，锁冲突概率高，并发度低

#### 5.2.2 元数据锁(MDL, Metadata Lock)
MySQL Server 层自动维护的锁，不需要手动加。当有事务在执行时，自动防止 DDL 操作(如 ALTER TABLE)破坏数据一致性。

示例：
1. 时间 10:00:00，事务 A 开始查询 users 表
2. 时间 10:00:05，执行 ALTER TABLE users ADD COLUMN ...，该操作会被阻塞
3. 时间 10:00:10，事务 A 结束，MDL 锁释放
4. 时间 10:00:11，ALTER 操作继续执行

#### 5.2.3 意向锁(Intention Lock)
这是 InnoDB 特有的一种表级锁，用来协调行锁和表锁的关系。

核心问题：事务 A 给某一行加了行锁。此时事务 B 想给整张表加表锁—它需要知道表里有没有行锁，总不能逐行检查吧？

意向锁就是解决方案：事务在加行锁之前，先给表加一个“意向锁”作为标识，告诉所有人“我打算在这张表的某些行上加锁”。

两种意向锁：

|意向锁|含义|触发场景|
|---|---|---|
|意向共享锁(IS)|事务打算对某些行加共享锁|SELECT ... LOCK IN SHARE MODE|
|意向排他锁(IX)|事务打算对某些行加排他锁|SELECT ... FOR UPDATE、UPDATE、DELETE|

意向锁之间的兼容性：

|锁类型|X|IX|S|IS|
|---|---|---|---|---|
|X|❌ 冲突|❌ 冲突|❌ 冲突|❌ 冲突|
|IX|❌ 冲突|✅ 兼容|❌ 冲突|✅ 兼容|
|S|❌ 冲突|❌ 冲突|✅ 兼容|✅ 兼容|
|IS|❌ 冲突|✅ 兼容|✅ 兼容|✅ 兼容|

 💡 关键理解：意向锁之间互相兼容，它们只是一个“通知标识”，不阻塞彼此。真正阻塞的是行锁本身。
 
### 5.3 行级锁(Row Lock)
行锁是 InnoDB 中粒度最小的锁，锁定的是索引记录，而不是数据行本身。

⚠️ 重要前提：InnoDB 的锁永远是加在索引上的。如果 SQL 没有命中任何索引，InnoDB 无法定位到具体行，会对全表所有记录加锁，退化为表级锁。

#### 5.3.1 共享锁(S Lock)与排他锁(X Lock)
这是行锁的两种基本类型：

|锁类型|别名|作用|加锁方式|
|---|---|---|---|
|共享锁(S)|读锁|允许持有者读取一行，其他事务也可以同时持有 S 锁读取| SELECT ... LOCK IN SHARE MODE |
|排他锁(X)|写锁|允许持有者更新或删除一行，其他事务不能加任何锁| SELECT ... FOR UPDATE、UPDATE、DELETE |

兼容性规则：
- S 锁和 S 锁：兼容(多个事务可以同时读)
- S 锁和 X 锁：冲突(读的时候不能写)
- X 锁和 X 锁：冲突(写的时候不能同时写)

#### 5.3.2 记录锁(Record Lock)
定义：锁定索引记录本身(即已经存在的某一行)。

触发场景：精确匹配唯一索引(如 WHERE id = 1)时，InnoDB 使用记录锁。

```
-- 假设 id 是主键
SELECT * FROM users WHERE id = 1 FOR UPDATE;  -- 对 id=1 这一行加 X 锁
```
#### 5.3.3 间隙锁(Gap Lock)
定义：锁定索引记录之间的“间隙”—即不存在的记录位置。

核心作用：防止其他事务在间隙中插入新记录，从而解决幻读问题。

触发场景：在可重复读(RR) 隔离级别下，范围查询未命中记录时。
```
-- 假设 users 表有 id: 1, 5, 10
SELECT * FROM users WHERE id BETWEEN 3 AND 7 FOR UPDATE;
-- 如果 id=3 和 id=7 都不存在，InnoDB 会锁定 (1,5) 和 (5,10) 之间的间隙
-- 阻止其他事务插入 id=3、4、6、7 等值
```
#### 5.3.4 临键锁(Next-Key Lock)
定义：记录锁 + 间隙锁的组合，锁定“记录本身”以及“记录前面的间隙”。

这是 InnoDB 在 RR 隔离级别下默认使用的锁类型，也是解决幻读的核心武器。

触发场景：在 RR 隔离级别下，范围查询命中记录时。
```
-- 假设 users 表有 id: 1, 5, 10
SELECT * FROM users WHERE id > 2 FOR UPDATE;
-- InnoDB 会锁住 id=5、id=10 这两条记录(记录锁)
-- 同时锁住 (1,5) 和 (5,10) 之间的间隙(间隙锁)
-- 组合起来就是临键锁
```
### 5.4 锁的粒度对比总结
| 锁类型 | 粒度      | 开销  | 并发度   | 死锁风险 | 适用引擎          |
| --- | ------- | --- | ----- | ---- | ------------- |
| 全局锁 | 整个数据库   | 极小  | 几乎为 0 | 无    | 所有引擎          |
| 表锁  | 整张表     | 小   | 低     | 无    | MyISAM、InnoDB |
| 意向锁 | 表级别(标识) | 小   | 高     | 无    | InnoDB        |
| 记录锁 | 单行索引记录  | 大   | 高     | 有    | InnoDB        |
| 间隙锁 | 索引间隙    | 大   | 中     | 有    | InnoDB(RR 下)  |
| 临键锁 | 记录 + 间隙 | 大   | 中     | 有    | InnoDB(RR 下)  |

## 六、锁与隔离级别的对应关系
理解了前面的内容后，我们用一张总表把“隔离级别 → 用什么锁 → 解决什么问题”串起来：

|隔离级别|使用的锁|间隙锁|幻读防护|核心特征|
|---|---|---|---|---|
|读未提交(RU)|仅记录锁|❌ 不生效|❌ 无|写加 X 锁，读不加锁，能读到未提交数据|
|读已提交(RC)|仅记录锁|❌ 不生效(外键/唯一约束除外)|❌ 无|语句级快照，每次 SELECT 生成新 Read View|
|可重复读(RR)|临键锁(记录锁+间隙锁)|✅ 生效|✅ 有(临键锁阻止插入)|事务级快照，首次 SELECT 生成 Read View 后沿用|
|串行化(S)|临键锁 + 表级意向锁|✅ 生效且更广|✅ 完全防护|所有查询自动加锁，串行执行|

核心结论：
- 隔离级别越高，锁的范围越大，并发性能越低。
- 隔离级别越低，越依赖 MVCC(而非锁)，并发性能越高，但对数据一致性的容忍度也越高。

## 七、死锁与排查
### 7.1 什么是死锁
死锁(Deadlock) 是指两个或多个事务互相等待对方持有的锁，导致所有事务都无法继续执行。

经典场景示例：
假设有一个 accounts 表，包含 id=1 和 id=2 两行数据。
1. 时间 10:00:00，事务 A 执行 UPDATE accounts SET balance = balance - 100 WHERE id = 1;，锁定 id=1 这一行
2. 时间 10:00:01，事务 B 执行 UPDATE accounts SET balance = balance - 100 WHERE id = 2;，锁定 id=2 这一行
3. 时间 10:00:02，事务 A 执行 UPDATE accounts SET balance = balance + 100 WHERE id = 2;，想要锁定 id=2，但被事务 B 持有，事务 A 进入等待
4. 时间 10:00:03，事务 B 执行 UPDATE accounts SET balance = balance + 100 WHERE id = 1;，想要锁定 id=1，但被事务 A 持有，事务 B 进入等待

此时：事务 A 等事务 B 释放 id=2，事务 B 等事务 A 释放 id=1，双方互相等待，永远无法结束—这就是死锁。

### 7.2 如何排查死锁
方法一：查看最近一次死锁信息
```
SHOW ENGINE INNODB STATUS\G
```
在输出中查找 `LATEST DETECTED DEADLOCK` 部分，可以看到：
- 发生死锁的事务 ID
- 各自持有的锁和等待的锁
- 被回滚的事务

方法二：查看当前锁等待情况(MySQL 8.0)
```
-- 查看当前锁信息
SELECT * FROM performance_schema.data_locks;

-- 查看锁等待关系
SELECT * FROM performance_schema.data_lock_waits;
```

方法三：查看当前运行的事务
```
SELECT * FROM INFORMATION_SCHEMA.INNODB_TRX\G
```

### 7.3 如何预防死锁
| 措施                             | 说明                                      |
| ------------------------------ | --------------------------------------- |
| 按相同顺序访问表/行                     | 所有事务都按同一顺序(如先 user 表再 order 表)操作，减少循环等待 |
| 使用 RC 隔离级别                     | RC 没有间隙锁，死锁概率远低于 RR                     |
| 缩短事务                           | 事务越短，持有锁的时间越短，死锁概率越低                    |
| 合理使用索引                         | 确保 SQL 命中索引，避免锁升级为表锁                    |
| 使用 SELECT ... FOR UPDATE 时注意顺序 | 尽量按主键顺序加锁                               |
### 7.4 配置最佳实践
```
[mysqld]
# ===== 事务隔离级别 =====
# MySQL 默认是 REPEATABLE-READ
# 互联网高并发场景建议改为 READ-COMMITTED(降低锁冲突和死锁风险)
transaction-isolation = READ-COMMITTED

# ===== 锁超时 =====
# 锁等待超时时间(秒)，默认 50 秒
innodb_lock_wait_timeout = 10

# ===== 死锁检测 =====
# 启用死锁检测(默认开启)
innodb_deadlock_detect = ON
```
**总结：** 事务隔离级别定义了“规则”，锁是实现规则的具体“手段”，MVCC 则在两者之间提供了“无锁并发”的第三条路。
- RC + 记录锁：互联网高并发首选，性能好，能防脏读，不防幻读
- RR + 临键锁：MySQL 默认，防脏读+防不可重复读+基本防幻读，但锁冲突和死锁风险更高
- 正确使用索引：锁是加在索引上的，没索引就会升级为表锁，性能雪崩
