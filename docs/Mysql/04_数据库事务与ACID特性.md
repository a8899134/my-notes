## 一、事务的概念
### 1.1 一个经典的“转账”难题
假设你要给朋友转账 100 元，数据库里要做两件事：
1. 你的账户：扣掉 100 元
2. 朋友的账户：增加 100 元

这两步必须要么都成功，要么都失败。如果第一步扣了你的钱，第二步因为系统崩溃没加上去，那这 100 元就“凭空消失”了—这是绝对不允许的。

事务(Transaction)，就是为了解决这类问题而生的。它把一组操作打包成一个不可分割的执行单元，这个单元要么全部完成，要么全部不完成。
### 1.2 事务结构
```
事务(Transaction)
    │
    ├── ACID 四大特性
    │     ├── A(原子性)→ 靠 undo log 实现
    │     ├── C(一致性)→ 靠约束 + 应用代码共同实现
    │     ├── I(隔离性)→ 靠锁 + MVCC 实现(4种隔离级别)
    │     └── D(持久性)→ 靠 redo log 实现
    │
    ├── 核心命令
    │     ├── START TRANSACTION / BEGIN  开启
    │     ├── COMMIT                     提交
    │     ├── ROLLBACK                   回滚
    │     └── SAVEPOINT / ROLLBACK TO   部分回滚
    │
    └── 并发问题(隔离级别逐级解决)
          脏读 ← 读未提交/读已提交 → 不可重复读 ← 可重复读 → 幻读 ← 串行化
```

## 二、事务的四大特性(ACID)
ACID 是事务的“四条铁律”，缺一不可。下面逐条拆解。
### 2.1 原子性(Atomicity)
#### 2.1.1 核心含义
原子性强调事务是一个不可分割的整体。事务中的所有操作，要么全部执行成功，要么全部不执行(回滚)。不存在“执行了一半”的状态。
#### 2.1.2 通俗理解
原子(Atom)在物理学中是最小不可分割的粒子。事务的原子性也一样—转账案例里，扣钱和加钱是一个整体，不能只做其中一个。如果中途出错，数据库会通过 undo log(回滚日志)，把已做的修改全部撤销，回到事务开始前的状态。
#### 2.1.3 实现原理简述
MySQL InnoDB 通过 undo log 实现原子性。每次修改数据前，先把修改前的旧值记录到 undo log 中。如果事务需要回滚，就用 undo log 里的旧值把数据恢复原状。
### 2.2 一致性(Consistency)
#### 2.2.1 核心含义
事务执行前后，数据库必须始终处于一致的状态—即所有数据都必须符合预定义的规则(主键唯一、外键约束、字段类型、触发器、业务逻辑等)。
#### 2.2.2 通俗理解
银行的账务系统有一条铁律：所有账户余额的总和必须等于总资产。无论你怎么转账(事务)，转账前这个等式成立，转账后这个等式也必须成立。如果事务执行后总账对不上了，说明一致性被破坏了。
#### 2.2.3 注意区分
原子性、隔离性、持久性是数据库“保证”的，而一致性是数据库和应用程序共同保证的。
- 数据库保证：约束(主键、外键、唯一性)、触发器、崩溃恢复
- 应用程序保证：正确的业务逻辑(比如转账金额不能为负数)
如果 SQL 写错了(比如只扣了你的钱，没加给对方)，数据库自身是“看不出”问题的，它只会照做—这时一致性就靠你的代码来守护。
### 2.3 隔离性(Isolation)
#### 2.3.1 核心含义
多个事务并发执行时，一个事务的内部操作对其他事务是不可见的。每个事务都像在独立的“隔间”里运行，互不干扰，直到它提交完成。
#### 2.3.2 通俗理解
银行有 10 个柜台窗口，10 个柜员同时处理不同客户的转账。隔离性保证：柜员 A 正在操作的账户余额，在提交之前，柜员 B 看不到 A 的修改。否则，A 还没转账完，B 就基于中间状态做了操作，账目会乱套。
#### 2.3.3 隔离性的“代价”
完全隔离(串行化)性能最差，宽松隔离(读未提交)性能最好但问题最多。数据库提供了四种隔离级别，让用户在“数据准确性”和“系统性能”之间做权衡。
### 2.4 持久性(Durability)
#### 2.4.1 核心含义
一旦事务提交成功，它对数据库所做的修改就永久保存下来。即使提交后立马断电、系统崩溃，数据也不会丢失。
#### 2.4.2 通俗理解
你在 ATM 上转账成功，打印了小票。这时候银行系统突然断电，重启后你的转账记录还在，钱不会凭空消失。这就是持久性的功劳。
#### 2.4.3 实现原理简述
MySQL InnoDB 通过 redo log(重做日志) 实现持久性。事务提交时，数据页可能还没刷到磁盘(Buffer Pool 中的脏页)，但 redo log 已经写入了磁盘。即使数据库宕机，重启后也能通过 redo log 把已提交事务的修改“重做”一遍，保证数据不丢。

## 三、事务的 SQL 命令实操
理解了 ACID 理论，我们来看 MySQL 中如何实际使用事务。
### 3.1 事务控制的三大核心命令
| 命令                         | 作用                | 通俗解释                 |
| -------------------------- | ----------------- | -------------------- |
| start transaction 或 begin； | 显式开启一个事务          | “准备开始记账，请记录我接下来所有操作” |
| commit；                    | 提交当前事务，让修改永久生效    | “我确认好了，请正式入账”        |
| rollback；                  | 回滚当前事务，撤销所有未提交的修改 | “出错了，请把我刚才的操作全部撤销”   |
### 3.2 自动提交(autocommit)
MySQL 默认开启了 autocommit = 1，意味着每条 SQL 语句都是一个独立的事务，执行完自动提交。
```
-- 查看自动提交状态(1=开启，0=关闭)
SHOW VARIABLES LIKE 'autocommit';

-- 关闭当前会话的自动提交
SET autocommit = 0;

-- 重新开启
SET autocommit = 1;
```
注意：关闭 autocommit 后，你必须手动执行 COMMIT 才能让修改生效，否则关闭连接时修改会自动回滚。
### 3.3 转账场景演示
假设有一个 `accounts` 表：
```
CREATE TABLE accounts (
    id INT PRIMARY KEY,
    name VARCHAR(20),
    balance DECIMAL(10,2)
);

INSERT INTO accounts VALUES (1, '张三', 1000.00), (2, '李四', 500.00);
```
场景：张三给李四转 200 元
```
-- 1. 开启事务
START TRANSACTION;

-- 2. 扣张三的钱
UPDATE accounts SET balance = balance - 200 WHERE id = 1;
-- 此时张三余额变为 800，但其他会话还看不到这个变化(取决于隔离级别)

-- 3. 加李四的钱
UPDATE accounts SET balance = balance + 200 WHERE id = 2;

-- 4. 检查一下余额是否非负(业务一致性检查)
SELECT balance FROM accounts WHERE id = 1;  -- 如果是负数，就要回滚

-- 5. 没问题，提交
COMMIT;

-- 如果中途发现异常(比如张三余额不足)，执行：
-- ROLLBACK;  -- 撤销上面的所有修改，回到 1000 和 500
```
### 3.4 保存点(SAVEPOINT)
有时候事务很长，你不想全部回滚，只想撤销某一步之后的操作。这时可以使用 保存点。
```
START TRANSACTION;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- 第一步
SAVEPOINT sp1;  -- 设置保存点

UPDATE accounts SET balance = balance - 50 WHERE id = 2;   -- 第二步(意外发现错了)
ROLLBACK TO SAVEPOINT sp1;  -- 回滚到 sp1，第二步撤销，第一步保留

COMMIT;  -- 提交，只生效第一步
```
1. SAVEPOINT 名称;在当前事务中设置一个标记点
2. ROLLBACK TO SAVEPOINT 名称;回滚到指定标记点，该点之后的修改全部撤销
3. RELEASE SAVEPOINT 名称;删除一个保存点(不常用)

## 四、事务在 MySQL 中的“引擎支持”
不是所有存储引擎都支持事务。建表时要注意：

|存储引擎|是否支持事务|说明|
|---|---|---|
|InnoDB|✅ 支持|MySQL 默认引擎，生产环境必选|
|MyISAM|❌ 不支持|不支持事务，也不支持外键，读多写少的老项目在用|
|Memory|❌ 不支持|重启数据丢失，仅做临时缓存|
```
-- 查看表的存储引擎
SHOW TABLE STATUS LIKE 'users';

-- 建表时指定引擎
CREATE TABLE orders (... ) ENGINE=InnoDB;
```
开发规范：所有涉及事务、外键、行锁的业务表，一律使用 ENGINE=InnoDB。
