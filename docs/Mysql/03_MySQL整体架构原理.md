## 一、MySQL 架构概览
你在命令行敲下一条 SELECT * FROM users WHERE id = 1;，MySQL是怎么把这条SQL变成你想要的那条数据的？
把MySQL想象成一家餐厅：
- 你 = 顾客(客户端)
- 服务员 = 连接器(接待你、核实身份，"门卫")
- 后厨菜单板 = 查询缓存(看看有没有现成的菜，已被淘汰的“快捷通道”)
- 配菜师傅 = 分析器(看懂你要点什么菜，看懂 SQL 的“翻译官”)
- 主厨 = 优化器(决定用什么方式做最快，制定“最佳路线”的主厨)
- 炒菜师傅 = 执行器(真的动手做，真正干活的“炒菜师傅”)
- 仓库 = 存储引擎(食材放哪、怎么拿，真正的“仓库管理员”)
一条SQL从进门到上菜，要经过上面每一个人。

## 二、MySQL 整体架构总览
### 2.1 分层设计
MySQL采用分层架构设计，核心分为两层：Server层和存储引擎层。
1. Server层：负责处理客户端连接、SQL语法解析、SQL优化、执行计划生成等通用逻辑。所有存储引擎共用这一层。
2. 存储引擎层：负责数据的实际存储和读取。采用插件式架构，可以灵活切换不同的存储引擎。
### 2.2 分层作用
这种设计的最大好处是职责分离—Server层不关心数据存在哪里、怎么存，只通过一套统一的API与存储引擎打交道。就像一台电脑，操作系统(Server层)不管你是机械硬盘还是固态硬盘(存储引擎)，只要接口对得上就能用。这也是MySQL能灵活切换InnoDB、MyISAM、Memory等存储引擎的核心原因。
### 2.3 一张图看懂全流程
一条SQL查询语句的执行路径大致如下：
```
客户端 → 连接器 → 查询缓存(8.0已移除) → 分析器 → 优化器 → 执行器 → 存储引擎 → 返回结果
```

## 三、Server 层核心组件
Server层是MySQL的大脑，所有SQL语句的通用处理逻辑都在这一层完成。
### 3.1 连接器
#### 3.1.1 核心作用
连接器是客户端访问MySQL的第一道关卡，负责：
1. 建立连接：与客户端完成 TCP 三次握手
2. 身份认证：校验用户名、密码、主机地址
3. 权限获取：认证通过后，从 mysql.user 系统表读取该用户的所有权限
4. 连接管理：维护连接的生命周期，管理空闲超时

**注意:** 连接建立后，即使管理员修改了该用户的权限，当前已建立的连接也不受影响。只有新建的连接才会加载新的权限配置。这意味着—如果你改了权限发现没生效，别慌，断开重连就好了。
#### 3.1.2 连接方式
最常用的连接命令：
```
mysql -h 110.110.110.110 -P 3306 -u root -p
```
参数含义
1. -h，数据库服务器 IP 地址(不写则默认 localhost)
2. -P，端口号(不写则默认 3306)
3. -u，用户名
4. -p，密码(可后面再输入，更安全)
#### 3.1.3 常用管理命令
| 命令                                  | 解释                |
| ----------------------------------- | ----------------- |
| SHOW PROCESSLIST;                   | 查看当前所有连接的状态       |
| SHOW FULL PROCESSLIST;              | 查看更详细的连接信息        |
| SHOW VARIABLES LIKE 'wait_timeout'; | 查看空闲连接超时时间(默认8小时) |
| SET SESSION wait_timeout = 3600;    | 将当前会话的空闲超时设为3600秒 |
| `KILL [connection_id];`             | 强制断开某个连接          |
| SELECT CONNECTION_ID();             | 查看当前连接的ID         |

**注意**：wait_timeout控制空闲连接的最大等待时间，超过这个时间连接器会自动断开。长连接虽然省去了反复握手的开销，但会累积内存—MySQL执行过程中使用的内存会挂在连接对象上，只有断开连接才会释放。建议定期断开空闲长连接，或使用mysql_reset_connection()重置连接资源。

### 3.2 查询缓存
这作用已经在 8.0 版本后被移除，
#### 3.2.1 核心作用
查询缓存以Key-Value形式缓存查询语句和结果集。Key是SQL语句，Value是结果集。如果同样的SQL再来一次，直接返回缓存结果，跳过后续所有步骤。
#### 3.2.2 淘汰原因
因为弊大于利：
- 只要对一个表做任何更新操作，这个表上的所有查询缓存都会被清空
- 对于更新频繁的表，缓存刚建好就被清掉，白白浪费内存和CPU
- 官方认为实际应用场景收益太低，MySQL 8.0正式移除了查询缓存模块
注意：如果你看的是MySQL 5.x的教程，里面提到查询缓存，可以跳过—新版本已经没有了。
### 3.3 分析器
#### 3.3.1 核心作用
没有命中缓存(或8.0版本直接跳过缓存)后，SQL就来到分析器。分析器要搞清楚两件事：
1. 词法分析
把SQL语句拆解成一个个“单词”，识别出：
- 这是什么类型的语句？(SELECT、INSERT、UPDATE、DELETE？)
- 要查哪个表？
- 要查哪些字段？
- 条件是什么？
2. 语法分析
根据 MySQL 的语法规则，判断 SQL 语句写得对不对。如果语法有误，会返回熟悉的错误信息：
```
ERROR 1064 (42000): You have an error in your SQL syntax
```
#### 3.3.2 通俗理解
分析器就像一个翻译官—你说了句中文(SQL)，他先听明白每个词是什么意思(词法分析)，再判断你说的这句话语法对不对(语法分析)。都对了，他才把这句话翻译成后厨能理解的指令。
### 3.4 优化器
#### 3.4.1 核心作用
分析器知道了你要“做什么”，优化器则决定“怎么做最快”。它的主要工作包括：
1. 选择索引：表里有多个索引时，决定用哪个最快
2. 决定JOIN顺序：多表关联时，决定先查哪个表、后查哪个表
3. 优化执行路径：选择成本最小的执行方案
优化器会基于表的统计信息(行数、索引分布等)来计算各种执行方案的成本，选出最优的那个。
#### 3.4.2 查看优化器的选择
可以用EXPLAIN命令查看优化器最终选择的执行计划：
```
EXPLAIN SELECT * FROM users WHERE age > 20;
```
EXPLAIN会告诉你：用了哪个索引、预计扫描多少行、表的连接顺序等—这是SQL性能调优最常用的命令。
### 3.5 执行器
#### 3.5.1 核心作用
执行器是真正执行SQL语句的模块。它按以下步骤工作：
1. 权限检查
执行前先确认你对这个表有没有执行操作的权限。如果没有，直接返回错误。
2. 调用存储引擎
权限通过后，执行器根据优化器生成的执行计划，调用存储引擎的API来读写数据。
3. 处理返回结果
对于查询语句，执行器逐行读取数据、过滤条件、提取字段，最后组装成结果集返回给客户端。
#### 3.5.2 执行器的“手艺”
执行器调用存储引擎的方式取决于有没有索引：
- 有索引：调用存储引擎的索引接口，快速定位数据
- 没有索引：调用全表扫描接口，逐行判断

## 四、存储引擎层
### 4.1 存储引擎概述
存储引擎负责数据的实际存储和读取。MySQL采用插件式架构，你可以在建表时指定使用哪种引擎。
常用存储引擎对比：

| 存储引擎   | 事务    | 行级锁   | 外键    | 适用场景             |
| ------ | ----- | ----- | ----- | ---------------- |
| InnoDB | ✅ 支持  | ✅ 支持  | ✅ 支持  | 高并发、需要事务(默认引擎)   |
| MyISAM | ❌ 不支持 | ❌ 表级锁 | ❌ 不支持 | 读多写少、不需要事务       |
| Memory | ❌ 不支持 | ❌ 表级锁 | ❌ 不支持 | 极速读写、数据可丢失(重启清空) |

指定存储引擎的方式：
```
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(50)
) ENGINE=InnoDB;
```
不写ENGINE的话，MySQL 5.5.5之后默认使用InnoDB。
### 4.2 InnoDB 存储引擎详解
InnoDB是目前最主流、最常用的存储引擎，下面重点拆解它的内部结构。InnoDB整体由内存结构、磁盘结构和后台线程三大部分组成。
#### 4.2.1 内存结构
InnoDB的内存架构分为四大模块：
##### 4.2.1.1 缓冲池(Buffer Pool)
这是InnoDB最重要的内存组件。
Buffer Pool是MySQL启动时向操作系统申请的一片连续内存区域，默认大小为128MB。它用来缓存：
- 数据页(表中的实际数据)
- 索引页(B+树的节点)
- undo 页(用于事务回滚)
- 自适应哈希索引
- 锁信息

读写流程：
- 读取数据：先查Buffer Pool，有就直接返回(避免磁盘IO)；没有则从磁盘加载到Buffer Pool再返回
- 修改数据：先修改Buffer Pool中的页(称为“脏页”)，再以一定频率刷回磁盘
一句话理解：Buffer Pool就是MySQL的“内存缓存”，让读写操作优先在内存中完成，极大减少了慢速的磁盘IO。

查看和调整Buffer Pool大小：
```
-- 查看当前Buffer Pool大小(单位：字节)
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';

-- 设置为2GB(需重启生效，或动态调整)
SET GLOBAL innodb_buffer_pool_size = 2147483648;
```
##### 4.2.1.2 更改缓冲区(Change Buffer)
针对非唯一二级索引的写入优化。
当修改的数据页不在Buffer Pool中时，Change Buffer会暂存这些修改操作，等以后该数据页被加载到Buffer Pool时再合并进去。这样可以减少随机IO，提升写入性能。
##### 4.2.1.3 自适应哈希索引(Adaptive Hash Index)
InnoDB会根据数据页的访问频率和模式，自动为热点数据页建立哈希索引。哈希索引的查询速度是O(1)，比B+树的O(log n)更快。
注意：这是InnoDB自动维护的，不需要DBA手动创建或管理。
##### 4.2.1.4 日志缓冲区(Log Buffer)
用于存储最近的数据更改记录(重做日志Redo Log)，直到这些记录被刷新到磁盘上的重做日志文件中。
日志缓冲区的大小由innodb_log_buffer_size控制，默认16MB。对于大批量数据操作，可以适当调大以减少磁盘写入次数。
```
SHOW VARIABLES LIKE 'innodb_log_buffer_size';
```
#### 4.2.2 磁盘结构
InnoDB在磁盘上存储以下几类文件：

|文件类型|说明|
|---|---|
|表结构文件(.frm)|存储表的定义信息(字段、索引等)|
|共享表空间(ibdata 1)|存储数据字典、undo 日志等公共数据|
|独立表空间(.ibd)|每个表独立的数据文件，存储数据和索引|
|重做日志文件(redo log)|记录数据变更，用于崩溃恢复|
|undo 日志|记录修改前的数据，用于事务回滚和 MVCC|
#### 4.2.3 后台线程
InnoDB使用多线程模型，后台有多个线程负责不同任务：

|线程|主要职责|
|---|---|
|Master Thread|核心后台线程，负责将Buffer Pool中的脏页异步刷盘、合并Change Buffer等|
|IO Thread|处理异步IO请求(读/写)|
|Purge Thread|清理不再需要的undo日志，回收空间|
|Page Cleaner Thread|专门负责脏页刷新(MySQL 5.6后从Master Thread分离)|

## 五、SQL 的完整生命旅程
把上面所有组件串起来，一条SQL查询语句的完整旅程是：
### 5.1 查询语句
select
```
1. 客户端发送SQL → 
2. 连接器：建立连接、验证身份和权限 → 
3. 查询缓存(8.0已移除)：检查是否有缓存结果 → 
4. 分析器：词法分析 + 语法分析，确认SQL合法 → 
5. 优化器：生成最优执行计划(选索引、定JOIN顺序)→ 
6. 执行器：检查表权限 → 调用存储引擎API → 
7. 存储引擎：从Buffer Pool或磁盘读取数据 → 
8. 执行器：过滤条件、提取字段 → 
9. 返回结果集给客户端
```
### 5.2 更新语句
包含 update、insert、delete。
更新语句比查询多了日志环节(涉及redo log和binlog的两阶段提交)，这里简要说明：
```
1-6步与查询相同 →
7. 执行器调用存储引擎，修改Buffer Pool中的数据页(标记为脏页)→
8. 写入redo log(prepare状态)→
9. 写入binlog → 
10. 提交事务，redo log改为commit状态 →
11. 后台线程择机将脏页刷回磁盘
```

**总结：**

MySQL = Server层(大脑：连接器→分析器→优化器→执行器)+ 存储引擎层(手脚：InnoDB负责真正存数据) 。

Server层管“想”(解析SQL、制定计划)，存储引擎层管“做”(读写数据)。两层之间通过标准API沟通，互不干扰—这也是MySQL能灵活替换存储引擎的奥秘所在。
