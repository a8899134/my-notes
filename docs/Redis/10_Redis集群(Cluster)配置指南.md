### 1.1 Redis 集群概念
Redis 集群(Cluster)是 Redis 官方提供的分布式解决方案，它通过数据分片(Sharding)和主从复制(Replication)来实现高可用性和横向扩展。

简单来说，集群模式解决了单机 Redis 和主从复制模式无法应对的两个核心问题：

|问题|单机/主从模式|集群模式|
|---|---|---|
|数据量超过单机内存|无法扩展|数据分散到多个节点，容量随节点数线性增长|
|写入性能瓶颈|单点写入|写入分散到多个主节点，吞吐量随节点数线性增长|
|高可用|主从+哨兵可实现|集群内置高可用，自动故障转移|

生活比喻：单机 Redis 就像一个小卖部，一个人看店，能服务的顾客有限，货架空间也有限。主从复制像是小卖部+仓库，有了备份但依然只有一个收银台。

Redis 集群就像连锁超市—每个分店(节点)都有一部分商品(数据)和收银员(主节点)，还有副店长(从节点)。顾客可以根据商品类型去不同的分店，客流分散，容量巨大，就算某个分店关门了，其他分店也能继续营业。
### 1.2 集群的核心特性
|特性|说明|
|---|---|
|数据分片|数据自动分散到多个节点，每个节点存储一部分数据|
|高可用|每个主节点至少有一个从节点，主节点故障时从节点自动升级|
|无中心化|客户端可连接任意节点，节点间通过 Gossip 协议通信|
|线性扩展|节点越多，集群总容量和吞吐量越高|
|自动故障转移|节点故障时自动检测并恢复|
### 1.3 集群的适用场景
|场景|是否适合|说明|
|---|---|---|
|数据量超过 50 GB|✅ 适合|单机内存装不下，需要分片|
|QPS 超过 5 万|✅ 适合|单机 CPU 成为瓶颈|
|需要高可用|✅ 适合|集群自带故障转移|
|数据量小(< 10 GB)|❌ 不建议|集群增加了运维复杂度，主从+哨兵足够|
|复杂多键操作频繁|⚠️ 谨慎|跨槽的多键操作受限|

## 二、集群的工作原理
### 2.1 数据分片与哈希槽
这是 Redis 集群最核心的机制。

Redis 集群将整个数据空间划分为 16384 个哈希槽(Hash Slot) 。每个键值对都属于这 16384 个槽中的一个，每个节点负责处理其中一部分槽。

分配逻辑：
```
当客户端存储一个键时：
1. 对键名进行 CRC16 校验
2. 将结果对 16384 取模
3. 得到的结果就是该键所属的哈希槽编号

计算公式：CRC16(key) % 16384 = 哈希槽编号
```
示例：
```text
键 "user:1001"  → CRC16 计算 → 12345 → 属于槽 12345
键 "order:2024" → CRC16 计算 → 5678  → 属于槽 5678
```
哈希槽分配示例：

|节点|负责的哈希槽范围|数量|
|---|---|---|
|节点 A(192.168.1.10:7001)|0 - 5460|5461 个|
|节点 B(192.168.1.11:7002)|5461 - 10922|5462 个|
|节点 C(192.168.1.12:7003)|10923 - 16383|5461 个|

哈希槽的优势：

|优势|说明|
|---|---|
|解耦数据与节点|数据只与槽有关，不直接绑定到节点|
|易于扩缩容|添加或删除节点时，只需移动槽，无需移动所有数据|
|管理单元|槽是数据迁移和负载均衡的基本单位|
### 2.2 节点角色与通信
|角色|职责|
|---|---|
|主节点(Master)|负责处理客户端读写请求，存储其所负责槽的数据|
|从节点(Replica)|主节点的副本，通过异步复制同步数据，主节点故障时升级为主节点|

节点间通信(Gossip 协议) ：

节点之间通过 Gossip 协议进行通信：
- 每个节点定期随机选择几个节点发送 PING 消息
- 接收方回复 PONG 消息
- 通信内容包含：节点状态、负责的哈希槽信息、集群配置信息
### 2.3 请求路由
客户端向集群发送请求时，有两种路由方式：
1. 方式一：重定向模式
```text
1. 客户端向任意节点(如节点 A)发送命令
2. 节点 A 计算该键所属的槽
3. 如果该槽由节点 A 负责 → 直接执行并返回结果
4. 如果该槽由节点 B 负责 → 节点 A 返回 MOVED 错误，告诉客户端去节点 B
5. 客户端收到 MOVED 后，向节点 B 重新发送请求
```
2. 方式二：智能客户端

成熟的 Redis 客户端(如 Lettuce、Jedis)会缓存槽与节点的映射关系，首次请求可能被重定向，后续请求直接命中正确的节点。

### 2.4 故障检测与自动故障转移
故障检测流程：
```text
1. 节点 A 定期向其他节点发送 PING
2. 如果节点 B 在超时时间内未响应 PONG
3. 节点 A 标记节点 B 为“疑似下线”(PFAIL)
4. 节点 A 通过 Gossip 将此信息传播给其他节点
5. 如果多数主节点都认为节点 B 不可达
6. 节点 B 被标记为“已下线”(FAIL)
7. 触发自动故障转移
```
自动故障转移流程：
```text
1. 主节点被标记为 FAIL
2. 该主节点下的从节点发起选举
3. 获得多数主节点投票的从节点胜出
4. 从节点升级为新的主节点
5. 新主节点接管原主节点的所有哈希槽
6. 其他节点更新集群状态
```
### 2.5 集群的端口说明
每个 Redis 集群节点需要两个 TCP 端口：

|端口类型|默认端口|用途|
|---|---|---|
|数据端口|6379(或自定义)|服务客户端请求，执行 Redis 命令|
|集群总线端口|数据端口 + 10000(如 16379)|节点间通信(故障检测、配置更新、故障转移等)|

防火墙配置要求：两个端口都必须在防火墙中开放，否则集群节点将无法正常通信。

## 三、环境规划
### 3.1 集群节点数量要求
Redis 集群至少需要 3 个主节点才能正常工作。生产环境建议采用 3 主 3 从 的架构(共 6 个节点)，实现高可用。
### 3.2 生产环境节点规划
| 角色    | IP 地址        | 数据端口 | 总线端口  | 说明               |
| ----- | ------------ | ---- | ----- | ---------------- |
| 主节点 1 | 192.168.1.10 | 7001 | 17001 | 负责槽位 0-5460      |
| 主节点 2 | 192.168.1.11 | 7002 | 17002 | 负责槽位 5461-10922  |
| 主节点 3 | 192.168.1.12 | 7003 | 17003 | 负责槽位 10923-16383 |
| 从节点 1 | 192.168.1.10 | 7004 | 17004 | 主节点 1 的备份        |
| 从节点 2 | 192.168.1.11 | 7005 | 17005 | 主节点 2 的备份        |
| 从节点 3 | 192.168.1.12 | 7006 | 17006 | 主节点 3 的备份        |

说明：为节省服务器资源，可以在 3 台物理机上各部署 2 个 Redis 实例(一个主节点 + 一个从节点)，也可以部署在 6 台独立的服务器上。生产环境建议将主从节点分布在不同的物理机上，避免单台物理机故障导致多个节点同时失效。

### 3.3 端口规划
|端口范围|用途|说明|
|---|---|---|
|7001-7006|数据端口|服务客户端请求|
|17001-17006|集群总线端口|节点间通信(数据端口 + 10000)|
### 3.4 前置条件
- 已完成 Redis 7.2.x 源码编译安装(参考《Redis 安装指南》)
- 所有节点网络互通
- 防火墙已放行数据端口和集群总线端口
- 所有节点上已创建数据目录(如 /var/lib/redis/7001/ 等)
- 建议各节点时间保持同步(NTP)

## 四、集群配置步骤
### 4.1 为每个节点创建配置文件
集群模式下，每个 Redis 实例需要独立的配置文件和数据目录。以下以节点 7001 为例：
1. 第一步：创建数据目录
```bash
sudo mkdir -p /var/lib/redis/7001
```
2. 第二步：创建配置文件
```bash
sudo vi /etc/redis/redis-7001.conf
```
3. 第三步：写入以下配置内容
```conf
# ============================ 基础配置 ============================

# 数据端口(每个节点不同)
port 7001

# 绑定地址(生产环境绑定内网 IP)
bind 192.168.1.10

# 后台运行(配合 systemd 时必须为 no)
daemonize no

# 日志文件
logfile /var/log/redis/redis-7001.log

# 数据目录(每个节点独立)
dir /var/lib/redis/7001

# 密码(所有节点统一)
requirepass YourStrongPassword2026!
masterauth YourStrongPassword2026!

# ============================ 集群配置 ============================

# 启用集群模式(关键配置)
cluster-enabled yes

# 集群配置文件(自动生成，不要手动修改)
cluster-config-file nodes-7001.conf

# 节点超时时间(毫秒)
cluster-node-timeout 5000

# ============================ 持久化配置 ============================

# 开启 AOF(生产环境建议)
appendonly yes
appendfsync everysec
```
### 4.2 为所有节点创建配置文件
按照上述模板，为 6 个节点分别创建配置文件，注意修改以下参数：

|节点|配置文件|数据目录|端口|bind IP|cluster-config-file|
|---|---|---|---|---|---|
|主 1| `/etc/redis/redis-7001.conf` | `/var/lib/redis/7001` |7001|192.168.1.10| `nodes-7001.conf` |
|主 2| `/etc/redis/redis-7002.conf` | `/var/lib/redis/7002` |7002|192.168.1.11| `nodes-7002.conf` |
|主 3| `/etc/redis/redis-7003.conf` | `/var/lib/redis/7003` |7003|192.168.1.12| `nodes-7003.conf` |
|从 1| `/etc/redis/redis-7004.conf` | `/var/lib/redis/7004` |7004|192.168.1.10| `nodes-7004.conf` |
|从 2| `/etc/redis/redis-7005.conf` | `/var/lib/redis/7005` |7005|192.168.1.11| `nodes-7005.conf` |
|从 3| `/etc/redis/redis-7006.conf` | `/var/lib/redis/7006` |7006|192.168.1.12| `nodes-7006.conf` |

提示：可以使用 sed 命令批量生成配置文件，避免手动逐个创建。

### 4.3 启动所有节点
1. 方式一：逐个启动(适用于少量节点)
```bash
# 在 192.168.1.10 上启动
sudo redis-server /etc/redis/redis-7001.conf
sudo redis-server /etc/redis/redis-7004.conf

# 在 192.168.1.11 上启动
sudo redis-server /etc/redis/redis-7002.conf
sudo redis-server /etc/redis/redis-7005.conf

# 在 192.168.1.12 上启动
sudo redis-server /etc/redis/redis-7003.conf
sudo redis-server /etc/redis/redis-7006.conf
```
2. 方式二：使用脚本批量启动
```bash
#!/bin/bash
# 启动所有集群节点
for port in 7001 7002 7003 7004 7005 7006; do
    redis-server /etc/redis/redis-${port}.conf
    echo "Started Redis node on port ${port}"
done
```
### 4.4 创建集群
所有节点启动后，使用 redis-cli --cluster create 命令创建集群。

命令格式：
```bash
redis-cli --cluster create \
    <节点1 IP:端口> \
    <节点2 IP:端口> \
    ... \
    --cluster-replicas <每个主节点的从节点数> \
    -a <密码>
```
实际命令示例：
```bash
redis-cli -a YourStrongPassword2026! \
    --cluster create \
    192.168.1.10:7001 \
    192.168.1.11:7002 \
    192.168.1.12:7003 \
    192.168.1.10:7004 \
    192.168.1.11:7005 \
    192.168.1.12:7006 \
    --cluster-replicas 1
```
命令参数说明：

|参数|说明|
|---|---|
| `-a 密码` |认证密码(所有节点统一)|
| `--cluster create` |创建集群命令|
| `节点列表` |所有节点的 IP 和端口|
| `--cluster-replicas 1` |每个主节点配 1 个从节点|

执行过程示例：
```text
>>> Performing hash slots allocation on 6 nodes...
Master[0] -> Slots 0 - 5460
Master[1] -> Slots 5461 - 10922
Master[2] -> Slots 10923 - 16383
Adding replica 192.168.1.10:7004 to 192.168.1.11:7002
Adding replica 192.168.1.11:7005 to 192.168.1.12:7003
Adding replica 192.168.1.12:7006 to 192.168.1.10:7001
>>> Trying to optimize replicas allocation for anti-affinity...
Can I set the above configuration? (type 'yes' to accept): yes
```
输入 yes 后，集群开始创建。完成后会显示：
```text
>>> Nodes configuration updated
>>> Assign a different config epoch to each node
>>> Sending CLUSTER MEET messages to join the cluster
>>> Cluster configuration completed
```

## 六、集群的日常运维
### 6.1 查看集群信息
| 命令              | 说明         |
| --------------- | ---------- |
| `CLUSTER INFO`  | 查看集群整体状态   |
| `CLUSTER NODES` | 查看所有节点信息   |
| `CLUSTER SLOTS` | 查看槽位分配情况   |
| `CLUSTER MYID`  | 查看当前节点的 ID |
### 6.2 添加新节点(扩容)
1. 第一步：启动新节点
准备一个新的 Redis 实例(如 192.168.1.13:7007)，配置 `cluster-enabled yes` 并启动。
2. 第二步：将新节点加入集群
```bash
redis-cli --cluster add-node 192.168.1.13:7007 192.168.1.10:7001 -a 密码
```
**命令说明**：
- `add-node`：添加节点命令
- 第一个参数：新节点的 IP 和端口
- 第二个参数：集群中任意现有节点的 IP 和端口(用于发现集群)

3. 第三步：为新节点分配哈希槽(重新分片)
```bash
redis-cli --cluster reshard 192.168.1.10:7001 -a 密码
```
执行后，按提示输入：
- 要迁移的槽数量(如 `1000`)
- 目标节点 ID(新节点的 ID)
- 源节点 ID(输入 `all` 表示从所有现有节点均匀迁移)
### 6.3 删除节点(缩容)
1. 第一步：将被删除节点的槽迁移到其他节点
```bash
redis-cli --cluster reshard 192.168.1.10:7001 -a 密码
```
将要删除节点上的所有槽迁移到其他节点。

2. 第二步：确认节点已无数据
```bash
redis-cli -h 192.168.1.13 -p 7007 -a 密码 CLUSTER NODES
# 确认该节点没有任何槽位
```
3. 第三步：从集群中移除节点
```bash
# 移除从节点
redis-cli --cluster del-node 192.168.1.10:7001 <要删除节点的ID> -a 密码

# 移除主节点(必须先迁移完所有槽)
redis-cli --cluster del-node 192.168.1.10:7001 <要删除节点的ID> -a 密码
```
### 6.4 重新平衡槽位
如果集群中某些节点的槽位过多或过少，可以重新平衡：
```bash
redis-cli --cluster rebalance 192.168.1.10:7001 -a 密码
```
### 6.5 检查集群健康
```bash
redis-cli --cluster check 192.168.1.10:7001 -a 密码
```
### 6.6 手动故障转移
如果需要维护某个主节点，可以手动触发故障转移：
```bash
# 连接到该主节点的从节点
redis-cli -h 192.168.1.10 -p 7004 -a 密码

# 执行手动故障转移
127.0.0.1:7004> CLUSTER FAILOVER
```

## 七、常见问题与解决方案
### 7.1 创建集群时报错
错误：`[ERR]` Node 192.168.1.10:7001 is not empty

原因：节点数据目录中残留了旧的 RDB/AOF 或集群配置文件。

解决方案：
```bash
# 停止节点
sudo redis-cli -p 7001 shutdown

# 清理数据目录
sudo rm -rf /var/lib/redis/7001/*

# 重新启动节点
sudo redis-server /etc/redis/redis-7001.conf
```
### 7.2 节点间无法通信
现象：集群创建失败，节点无法互相发现。

原因：
- 防火墙未放行集群总线端口
- 配置文件中 bind 地址不正确

解决方案：
```bash
# 检查防火墙状态
sudo firewall-cmd --list-ports

# 放行数据端口和总线端口
sudo firewall-cmd --permanent --add-port=7001-7006/tcp
sudo firewall-cmd --permanent --add-port=17001-17006/tcp
sudo firewall-cmd --reload

# 检查配置文件中的 bind 地址
grep "^bind" /etc/redis/redis-*.conf
```
### 7.3 跨槽多键操作失败
现象：执行 MGET、MSET、SUNION 等涉及多个键的命令时报错。

原因：这些键不属于同一个哈希槽，集群无法跨槽执行多键操作。

解决方案：使用哈希标签(Hash Tag) 强制多个键属于同一个槽。
```bash
# 使用哈希标签 {user_id} 确保所有相关键在同一个槽
SET {1001}:name "张三"
SET {1001}:age "25"
MGET {1001}:name {1001}:age  # 可以正常执行
```
### 7.4 集群脑裂(Split-Brain)
现象：网络分区导致集群中出现多个主节点。

原因：网络故障导致部分节点与集群失联，失联的主节点继续接收写入。

解决方案：
- 配置合理的 cluster-node-timeout(如 5000-15000 毫秒)
- 监控网络质量，避免频繁的网络抖动
- 使用 min-replicas-to-write 限制写入条件
### 7.5 槽位分配不均
现象：部分节点负载过高，部分节点空闲。

解决方案：
```bash
# 查看槽位分布
redis-cli --cluster info 192.168.1.10:7001 -a 密码

# 重新平衡
redis-cli --cluster rebalance 192.168.1.10:7001 -a 密码
```

## 八、生产环境最佳实践
### 8.1 集群规模建议
| 场景     | 节点数量             | 说明           |
| ------ | ---------------- | ------------ |
| 最小生产集群 | 3 主 + 3 从(6 节点)  | 可容忍 1 个主节点故障 |
| 中型集群   | 5 主 + 5 从(10 节点) | 可容忍 2 个主节点故障 |
| 大型集群   | 9 主 + 9 从(18 节点) | 可容忍 4 个主节点故障 |
| 最大规模   | 最多 1000 个节点      | 官方设计上限       |
### 8.2 配置建议
| 配置项                               | 建议值           | 说明       |
| --------------------------------- | ------------- | -------- |
| `cluster-node-timeout`            | 5000-15000 毫秒 | 节点故障判定时间 |
| `cluster-replica-validity-factor` | 10            | 从节点有效性因子 |
| `cluster-migration-barrier`       | 1             | 副本迁移屏障   |
| `repl-backlog-size`               | 64mb-256mb    | 复制积压缓冲区  |
| `maxmemory`                       | 物理内存的 60%-75% | 内存限制     |
### 8.3 安全建议
| 建议      | 说明                                                                                                |
| ------- | ------------------------------------------------------------------------------------------------- |
| 统一密码    | 所有节点 `requirepass` 和 `masterauth` 一致                                                              |
| 绑定内网 IP | 禁止 `bind 0.0.0.0`                                                                                 |
| 防火墙限制   | 仅允许内网 IP 访问数据端口和总线端口 |
| 禁用危险命令  | 重命名或禁用 `FLUSHALL`、`FLUSHDB`、`CONFIG`                                                              |
| 定期备份    | 在从节点执行 `BGSAVE` 备份                                                                                |
### 8.4 监控建议
| 监控项  | 告警条件                     | 说明     |
| ---- | ------------------------ | ------ |
| 集群状态 | `cluster_state != ok`    | 集群异常   |
| 节点状态 | 节点 `fail` 或 `pfail`      | 节点故障   |
| 槽位状态 | `cluster_slots_fail > 0` | 有槽位不可用 |
| 内存使用 | 超过 maxmemory 的 80%       | 接近内存上限 |

## 9、总结
### 9.1 核心要点
1. 集群模式是 Redis 官方提供的分布式解决方案，通过数据分片实现横向扩展
2. 至少需要 3 个主节点才能组成集群
3. 16384 个哈希槽是集群的核心机制，每个节点负责一部分槽
4. 每个主节点至少配一个从节点，实现高可用
5. 两个端口必须开放：数据端口和集群总线端口
6. 跨槽多键操作受限，需要使用哈希标签
### 9.2 主从复制 vs 哨兵 vs 集群
| 对比维度 | 主从复制  | 哨兵模式       | 集群模式          |
| ---- | ----- | ---------- | ------------- |
| 数据容量 | 单机限制  | 单机限制       | 可水平扩展         |
| 高可用  | 需手动切换 | 自动故障转移     | 自动故障转移        |
| 读写分离 | 支持    | 支持         | 支持            |
| 数据分片 | 不支持   | 不支持        | 支持            |
| 复杂度  | 低     | 中          | 高             |
| 适用场景 | 数据量小  | 数据量中等、需高可用 | 数据量大、需高可用和高吞吐 |
