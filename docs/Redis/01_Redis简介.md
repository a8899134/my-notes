## 一、Redis 概念
### 1.1 Redis 基本概念
Redis(Remote Dictionary Server，远程字典服务)是一款开源的、高性能的键值对(Key-Value)内存数据库，由 ANSI C 编写，核心定位是「高性能缓存 + 轻量级存储 + 分布式中间件」，是生产环境中最主流的内存中间件之一。
通俗地说，Redis 就像一个超级快速的巨型字典：
- 你给它一个“词”(Key，键)，它就能立刻告诉你对应的“解释”(Value，值)
- 所有数据都存放在内存(也就是电脑的运行内存)里，所以查询速度极快
- 但它也不是用完就丢—它可以把内存里的数据保存到硬盘上，服务器重启后还能恢复
### 1.2 Redis 核心特点
1. **基于内存：** 数据读写直接操作内存，速度极快。官方基准测试可达 10 万+ QPS(每秒查询次数)。
2. **支持持久化：** 可将内存数据保存到硬盘，服务器重启后恢复，防止数据丢失。
3. **丰富的数据类型：** 不限于简单的键值对，支持字符串(String)、哈希(Hash)、列表(List)、集合(Set)、有序集合(Sorted Set)等。
4. **单线程架构：** 核心命令处理采用单线程，避免了多线程的竞争和上下文切换开销。
5. **丰富的功能：** 支持键过期(TTL)、发布/订阅(Pub/Sub)、事务、Lua 脚本等高级特性。
6. **主从复制与高可用：** 支持数据复制，可搭建哨兵(Sentinel)或集群(Cluster)架构，保证服务高可用。
7. **原子操作：** Redis 的单个命令操作是原子性的，要么成功要么失败，不会出现中间状态
### 1.3 Redis 的典型应用
- 缓存加速：将频繁查询但变更不频繁的数据(如用户信息、商品详情)放入 Redis，能大幅减轻数据库压力，加快网页或 APP 的响应速度。
- 实时计数器：利用 Redis 的原子自增操作，可以轻松实现文章阅读数、视频播放量、网站活跃用户数(UV)等实时统计。
- 排行榜系统：利用有序集合(Sorted Set)，能快速实现游戏积分榜、热门商品榜单等需要排序的功能。
- 消息队列：利用列表(List)或流(Stream)数据结构，可以实现简单的消息队列，用于异步处理任务，如发送邮件、生成图片缩略图等。
- 分布式会话管理：在分布式系统中，将用户的登录状态(Session)集中存储到 Redis，可以实现多台服务器间的会话共享。

## 二、Redis 的数据类型
Redis 中所有的 Key(键)都是字符串类型，而 Value(值) 则支持多种不同的数据类型。下面详细介绍五种最常用的数据类型。

| 核心数据结构 | 核心特性 | 典型应用 |
|--------------|----------|----------|
| String | 二进制安全，可存字符串 / 数字 / 二进制(最大 512 MB) | 令牌缓存、计数器、简单配置存储 |
| Hash | 键值对集合，适合存储对象(如用户信息) | 用户信息、商品属性、订单详情 |
| List | 有序可重复列表，支持头尾快速操作 | 消息队列、最新消息列表、评论流 |
| Set | 无序不可重复集合，支持交集 / 并集 / 差集 | 去重、好友共同关注、抽奖活动 |
| ZSet(Sorted Set) | 有序不可重复集合，按分数排序 | 排行榜、延迟队列、接口限流 |
| 扩展结构 | GEO(地理空间)、BitMap(位图)、HyperLogLog(基数统计) | 附近的人、用户签到、UV 统计 |

## 三、Redis 核心机制
### 3.1 持久化机制
Redis 提供两种核心持久化方式，生产环境通常 “混合使用”：
- RDB(Redis Database)：定时将内存数据生成快照(dump.rdb)写入磁盘，恢复速度快，但可能丢失快照间隔内的数据；
- AOF(Append Only File)：记录所有写命令到日志文件(appendonly.aof)，实时性高，恢复时重新执行命令即可；
- 混合持久化：AOF 文件中包含 RDB 快照 + 增量 AOF 命令，兼顾恢复速度和数据完整性(Redis 4.0+ 默认推荐)。
### 3.2 过期与淘汰策略
- 过期策略：支持为 Key 设置过期时间，通过 “主动过期(访问时检查)+ 被动过期(后台线程定期扫描)” 清理过期 Key；
- 内存淘汰：当内存达到上限时，按预设策略淘汰 Key(生产常用 allkeys-lru：淘汰最少使用的 Key)，避免耗尽系统内存。
### 3.3 单线程模型
Redis 核心网络 IO、命令执行采用单线程，避免多线程上下文切换开销；同时通过 “IO 多路复用(epoll/kqueue)” 处理大量并发连接，兼顾 “高性能” 与 “线程安全”。
**补充：** Redis 6.0+ 引入多线程 IO，仅用于网络收发，命令执行仍为单线程，进一步提升吞吐量。

## 四、Redis 的架构模式
### 4.1 单机模式
单个 Redis 节点提供服务，适用于数据量小、并发量低的场景。优点是部署简单，缺点是一旦故障则服务不可用。
### 4.2 主从复制模式
一个主节点(Master)负责写操作，多个从节点(Slave)同步数据并负责读操作，实现读写分离和数据冗余。主节点故障时需手动切换。
### 4.3 哨兵模式(Sentinel)
在主从复制的基础上增加了哨兵进程，用于监控节点健康状态。当主节点故障时，哨兵会自动选举新的主节点，实现自动故障转移，保证高可用。
### 4.4 集群模式(Cluster)
数据自动分片到多个节点，每个节点存储一部分数据，支持水平扩展。适用于数据量大、高吞吐量的生产环境。Redis 7.2.x 对集群模式有良好的支持。

## 五、局限性与注意事项
### 5.1 内存容量限制
Redis 的数据全部存储在内存中，因此总数据量受服务器内存大小限制。当数据量超过可用内存时，需要扩容或使用集群方案。
### 5.2 数据一致性风险
作为缓存使用时，Redis 中的数据与数据库中的数据可能存在短暂不一致。生产环境需要设计合理的缓存更新策略(如 Cache-Aside、Write-Through)。
### 5.3 持久化有性能损耗
开启 RDB 或 AOF 持久化会占用一定的 CPU 和磁盘 I/O 资源，在数据量大时需要评估性能影响。
### 5.4 单线程的局限
虽然 Redis 核心命令处理是单线程的，但 6.0 版本开始在网络 I/O 层面引入了多线程。对于单个慢命令(如 KEYS 、大 key 的删除)，仍可能阻塞其他请求。
### 5.5 许可证变更
2024 年起，Redis 官方将新版本许可证从 BSD 变更为 RSALv 2 和 SSPLv 1，不再完全开源。但 7.2.x 及之前版本仍使用 BSD-3-Clause 许可证，可免费使用。

## 六、Redis 与 MySQL
| 对比维度    | Redis             | MySQL         |
| ------- | ----------------- | ------------- |
| 数据存储位置  | 内存(主要)+ 硬盘(持久化)   | 硬盘(主要)        |
| 读写速度    | 极快(微秒级)           | 较慢(毫秒级)       |
| 支持的数据结构 | 多种(字符串、哈希、列表、集合等) | 表格(行+列)       |
| 查询语言    | 命令(如 SET、GET)     | SQL           |
| 事务支持    | 有限(不支持回滚)         | 完整(ACID)      |
| 数据容量    | 受内存大小限制           | 可支持 TB 级别硬盘存储 |
| 持久化保障   | 最终一致性(可配置)        | 强一致性          |
| 典型角色    | 缓存、辅助存储           | 主存储、核心数据      |
简单总结：MySQL 负责存"全部数据"，Redis 负责存"热点数据"。两者通常配合使用，而非互相替代。

## 七、总结
Redis 不是传统数据库的 “替代品”，而是 “高性能补充”：

- 核心优势：内存级读写速度 + 多数据结构适配 + 轻量易部署 + 高可用；
- 核心定位：高性能缓存 + 轻量级存储 + 分布式协调组件;
- 核心价值：解决高并发场景下的性能问题，适配传统数据库无法高效处理的业务场景。

简单来说：Redis 是 “快” 的代名词，凡是需要 “高性能读写、高频计数、实时排序” 的场景，Redis 都是首选方案。
