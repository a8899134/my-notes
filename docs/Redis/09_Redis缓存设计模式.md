## 一、缓存设计模式概述
### 1.1 缓存设计模式概念
缓存设计模式是指在应用程序中使用缓存时，总结出来的一系列可复用的最佳实践方案。它解决了“什么时候读缓存、什么时候写缓存、缓存与数据库如何保持一致”等核心问题。

生活比喻：缓存设计模式就像图书馆的“图书预约系统”。
- 读者借书时，先查预约系统(缓存)，有就直接取走
- 没有预约记录，再去书库找(数据库)，找到后同步更新预约系统
- 还书时，先还回书库(数据库)，再更新预约系统(缓存)
- 新书上架时，先在书库登记(数据库)，再添加到预约系统(缓存)
没有这套规则，图书管理员会手忙脚乱；有了这套规则，一切井然有序。
### 1.2 模式的作用
|问题|没有设计模式|有设计模式|
|---|---|---|
|缓存与数据库一致性|数据混乱，缓存与数据库不同步|有明确的一致性和更新策略|
|缓存命中率|随机缓存，命中率低|针对热点数据缓存，命中率高|
|系统复杂度|每个开发者各写一套逻辑，维护困难|统一的模式，易于理解和维护|
|异常应对|缓存雪崩、穿透、击穿频发|有成熟的应对方案|
### 1.3 模式的分类
```text
缓存设计模式
├── 核心缓存模式
│   ├── Cache-Aside(旁路缓存)— 最常用
│   ├── Read-Through(读穿透)
│   └── Write-Through / Write-Behind(写穿透 / 写回)
├── 缓存更新策略
│   ├── Cache-Aside 更新策略
│   ├── 延迟双删
│   └── 订阅 Binlog 更新
├── 缓存异常应对
│   ├── 缓存雪崩(Cache Avalanche)
│   ├── 缓存穿透(Cache Penetration)
│   └── 缓存击穿(Cache Breakdown)
└── 缓存预热(Cache Warming)
```

## 二、核心缓存模式
### 2.1 Cache-Aside
#### 2.1.1 基本概念
Cache-Aside(旁路缓存模式) 是最常用的缓存设计模式。应用程序负责同时管理缓存和数据库，在读取数据时先查缓存，缓存命中则直接返回；缓存未命中则查询数据库，将结果写入缓存后再返回。
生活比喻：Cache-Aside 就像“点外卖时的备餐流程”。
- 你先看手机上的“历史订单”(缓存)，有就直接点
- 没有历史记录，你打电话问餐厅今天有什么菜(数据库)
- 问完后把菜名记在手机里(写入缓存)，下次直接点
#### 2.1.2 读流程
```text
					┌─────────────────────────────────────┐
                    │             应用请求读数据           │
                    └─────────────────┬───────────────────┘
                                      │
                                      ▼
                    ┌─────────────────────────────────────┐
                    │            先查 Redis 缓存           │
                    └─────────────────┬───────────────────┘
                                      │
                        ┌─────────────┴─────────────┐
                        │                           │
                        ▼                           ▼
              ┌─────────────────┐         ┌─────────────────────┐
              │   缓存命中       │         │    缓存未命中     	│
              │  返回缓存数据     │         │    查 MySQL        │
              └─────────────────┘         └──────────┬──────────┘
                                                      │
                                                      ▼
                                        ┌─────────────────────────┐
                                        │    将数据写入 Redis      │
                                        │   (设置过期时间)        │
                                        └──────────┬──────────────┘
                                                   │
                                                   ▼
                                        ┌─────────────────────────┐
                                        │      返回数据给应用       │
                                        └─────────────────────────┘

```
#### 2.1.3 写流程
```text
应用写入数据 → 先更新数据库 → 再删除缓存(或更新缓存)
```
读流程的代码示例(伪代码)：
```python
def get_user(user_id):
    # 1. 先查 Redis 缓存
    cache_key = f"user:{user_id}"
    user_data = redis.get(cache_key)
    
    if user_data:
        # 缓存命中，直接返回
        return user_data
    
    # 2. 缓存未命中，查数据库
    user_data = mysql.query("SELECT * FROM users WHERE id = ?", user_id)
    
    if user_data:
        # 3. 写入缓存，设置过期时间(如 1 小时)
        redis.setex(cache_key, 3600, user_data)
    
    return user_data
```
写流程的代码示例(伪代码)：
```python
def update_user(user_id, new_data):
    # 1. 先更新数据库
    mysql.update("UPDATE users SET name = ? WHERE id = ?", new_data, user_id)
    
    # 2. 再删除缓存(让下次读请求重建缓存)
    redis.delete(f"user:{user_id}")
```
#### 2.1.4 Cache-Aside 的优缺点
|优点|缺点|
|---|---|
|实现简单，容易理解|缓存与数据库存在短暂不一致|
|缓存的命中率可控|写操作需要维护缓存一致性|
|适合读多写少的场景|首次查询会穿透到数据库|
|应用程序完全控制缓存行为|需要处理并发更新冲突|
#### 2.1.5 适用场景
- 大部分业务场景(用户信息、商品详情、订单数据等)
- 读多写少的数据
- 对数据一致性要求不是极致严格的场景
### 2.2 Read-Through
#### 2.2.1 基本概念
Read-Through (读穿透模式)模式中，应用程序不直接访问缓存和数据库，而是通过一个缓存中间件(缓存抽象层) 来读取数据。当缓存未命中时，中间件负责从数据库加载数据并写入缓存，应用程序完全感知不到数据库的存在。
生活比喻：Read-Through 就像“在餐厅点菜”。
- 你(应用程序)只看菜单(缓存中间件)，不直接进厨房(数据库)
- 如果菜单上有这道菜(缓存命中)，服务员直接端上来
- 如果菜单上没有(缓存未命中)，服务员去厨房告诉厨师做(中间件查数据库)，做好后端上来
- 你从头到尾都不知道厨房在哪里
#### 2.2.2 工作流程
```text
					┌─────────────────────────────────────┐
                    │             应用请求读数据           │
                    └─────────────────┬───────────────────┘
                                      │
                                      ▼
                    ┌─────────────────────────────────────┐
                    │      缓存中间件(抽象层)             │
                    │   (应用程序只与中间件交互)           │
                    └─────────────────┬───────────────────┘
                                      │
                        ┌─────────────┴─────────────┐
                        │                           │
                        ▼                           ▼
              ┌─────────────────┐         ┌─────────────────────┐
              │   缓存命中       │         │    缓存未命中        │
              │  返回缓存数据     │         │  中间件查数据库      │
              └─────────────────┘         └──────────┬──────────┘
                                                      │
                                                      ▼
                                        ┌─────────────────────────┐
                                        │  中间件将数据写入缓存     │
                                        └──────────┬──────────────┘
                                                   │
                                                   ▼
                                        ┌─────────────────────────┐
                                        │  中间件返回数据给应用     │
                                        └─────────────────────────┘
```
#### 2.2.3 Read-Through 与 Cache-Aside 的区别
| 对比维度    | Cache-Aside | Read-Through               |
| ------- | ----------- | -------------------------- |
| 谁负责查数据库 | 应用代码        | 缓存中间件                      |
| 谁负责写入缓存 | 应用代码        | 缓存中间件                      |
| 应用复杂度   | 较高(需要写缓存逻辑) | 较低(只调用中间件)                 |
| 灵活性     | 高(应用可自由控制)  | 低(受中间件限制)                  |
| 典型实现    | 自研代码        | Spring Cache、MyBatis Cache |
#### 2.2.4 适用场景
- 使用 Spring Cache、MyBatis Cache 等框架的应用
- 希望将缓存逻辑与业务逻辑分离
- 不希望应用代码直接操作缓存
### 2.3 Write-Through
#### 2.3.1 基本概念
Write-Through (写穿透模式)模式中，应用程序只与缓存中间件交互。写入数据时，中间件先更新缓存，再同步更新数据库。写入操作是同步的，确保缓存和数据库同时更新。

生活比喻：Write-Through 就像“公司请假流程”。
- 你(应用程序)在 OA 系统提交请假申请(写操作)
- OA 系统(缓存中间件)先在系统中记录(更新缓存)，再同步推送到 HR 系统(更新数据库)
- 两边的记录是同步完成的，确保数据一致
#### 2.3.2 工作流程
```text
应用发起写请求 → 缓存中间件接收 → 更新缓存 → 同步更新数据库 → 返回成功
```
#### 2.3.3 Write-Through 的优缺点
| 优点         | 缺点            |
| ---------- | ------------- |
| 缓存与数据库实时一致 | 写操作延迟较高(同步写入) |
| 应用代码简单     | 数据库写入慢会影响整体性能 |
| 缓存不会过期失效   | 不适合高频写入场景     |
#### 2.3.4 适用场景
- 对数据一致性要求高的场景
- 写入频率较低的场景
- 使用 Spring Cache 等框架的应用
### 2.4 Write-Behind
Write-Behind(写回模式) 模式中，应用程序将数据写入缓存后立即返回，缓存中间件在后台异步将数据同步到数据库。写入操作是异步的，写入性能极高。

生活比喻：Write-Behind 就像“快餐店订单系统”。
- 你(应用程序)点餐后，前台在系统里记录(写入缓存)，然后告诉你“好了，请稍等”(立即返回)
- 后厨(数据库)按顺序慢慢制作(异步同步)
- 不会因为后厨忙而让顾客在前台排队等待
#### 2.4.2 工作流程
```text
应用发起写请求 → 写入缓存 → 立即返回成功
                              ↓
                   后台异步批量写入数据库
```
#### 2.4.3 Write-Behind 的优缺点
| 优点            | 缺点               |
| ------------- | ---------------- |
| 写入性能极高        | 缓存宕机可能丢失未同步的数据   |
| 可批量写入，减少数据库压力 | 数据存在延迟不一致窗口      |
| 适合高并发写入场景     | 实现复杂，需要处理重试和失败恢复 |
#### 2.4.4 适用场景
- 日志收集系统
- 计数器和统计系统
- IoT 设备数据采集
- 对短期数据丢失容忍的场景

## 三、缓存更新策略
### 3.1 缓存更新策略的三种模式
|策略|说明|一致性|复杂度|
|---|---|---|---|
|先更新数据库，再删除缓存|Cache-Aside 标准写法|较高|低|
|先更新数据库，再更新缓存|直接更新缓存值|较高|中|
|先删除缓存，再更新数据库|并发下易产生脏数据|较低|低|
生产环境建议：使用 “先更新数据库，再删除缓存” 方案，这是最成熟可靠的方式。
### 3.2 延迟双删
#### 3.2.1 基本概念
延迟双删是一种解决“先更新数据库，再删除缓存”方案中并发读写导致脏数据的优化策略。
核心思想：删除缓存后，延迟一段时间再次删除，确保并发请求产生的旧缓存数据被清除。
#### 3.2.2 执行流程
```text
1. 应用更新数据库
2. 删除缓存(第一次)
3. 延迟 N 毫秒(通常 100-500ms)
4. 再次删除缓存(第二次)
```
代码示例(伪代码)：
```python
def update_user(user_id, new_name):
    # 1. 更新数据库
    db.update("UPDATE users SET name = ? WHERE id = ?", new_name, user_id)
    
    # 2. 删除缓存(第一次)
    redis.delete(f"user:{user_id}")
    
    # 3. 延迟 200ms
    time.sleep(0.2)
    
    # 4. 再次删除缓存(第二次)
    redis.delete(f"user:{user_id}")
```
#### 3.2.3 为什么需要延迟双删
在并发场景下，如果不做延迟双删，可能出现以下时序：
```text
时间线：
T1: 线程A 更新数据库(name = '张三')
T2: 线程A 删除缓存
T3: 线程B 读取数据，缓存未命中，查数据库得到 '张三'
T4: 线程B 将 '张三' 写入缓存(这是旧数据！)
T5: 线程A 完成更新操作

结果：缓存中存的是旧数据 '张三'，与数据库不一致。
```
延迟双删的效果：
```text
时间线：
T1: 线程A 更新数据库(name = '张三')
T2: 线程A 删除缓存(第一次)
T3: 线程B 读取数据，缓存未命中，查数据库得到 '张三'
T4: 线程B 将 '张三' 写入缓存(旧数据)
T5: 线程A 等待 200ms 后，再次删除缓存(第二次)
T6: 后续请求缓存未命中，重新加载新数据

结果：缓存中的旧数据被清除，数据最终一致。
```
#### 3.2.4 适用场景
- 并发读写频繁的场景
- 对数据最终一致性要求较高的场景
- 缓存数据更新不频繁但读取频繁的场景
### 3.3 订阅 Binlog 更新缓存
#### 3.3.1 基本概念
通过订阅数据库的 Binlog(二进制日志)，监听数据变更事件，在数据变更时自动更新或删除缓存。
生活比喻：订阅 Binlog 就像“微信公众号订阅”。
- 微信公众号(数据库)发布新文章(数据变更)
- 你订阅了公众号(监听 Binlog)，收到推送通知
- 你根据通知内容做出响应(更新缓存)
#### 3.3.2 工作流程
```text
数据库更新 → 生成 Binlog → 监听组件(如 Canal)捕获变更 → 触发缓存更新/删除
```
典型架构：
```text
MySQL Binlog → Canal → MQ → 消费者 → Redis(更新/删除缓存)
```

|组件|作用|
|---|---|
|MySQL Binlog|记录所有数据变更|
|Canal(阿里开源)|监听 MySQL Binlog，推送变更事件|
|MQ(消息队列)|异步解耦，保证可靠消费|
|消费者|根据变更事件更新或删除 Redis 缓存|
#### 3.3.3 优缺点
|优点|缺点|
|---|---|
|缓存与数据库完全解耦|架构复杂，需要额外组件|
|数据变更自动触发缓存更新|有短暂延迟(Binlog 同步延迟)|
|无需修改业务代码|需要维护 Canal、MQ 等组件|
|适合微服务架构|故障排查链路较长|
#### 3.3.4 适用场景
- 微服务架构
- 多应用共享同一套缓存
- 业务代码不方便修改

## 四、缓存异常场景与应对
### 4.1 缓存雪崩(Cache Avalanche)
#### 4.1.1 基本概念
缓存雪崩是指大量缓存 Key 在同一时间失效，导致大量请求直接穿透到数据库，瞬间压垮数据库。
生活比喻：缓存雪崩就像“超市限时抢购活动”。
- 超市宣布：所有商品在中午 12 点开始打折(缓存同时失效)
- 12 点一到，成千上万的顾客同时涌入超市(大量请求打到数据库)
- 超市收银台(数据库)瞬间被挤爆
#### 4.1.2 原因分析
| 原因          | 说明             |
| ----------- | -------------- |
| 缓存设置相同的过期时间 | 大量 Key 在同一时刻过期 |
| Redis 节点故障  | 整个缓存不可用        |
| 缓存服务重启      | 重启后缓存为空        |
#### 4.1.3 解决方案
1. 方案一：缓存过期时间添加随机值
```python
import random

# 在原过期时间基础上增加随机偏移量(如 ±10%)
base_ttl = 3600  # 1 小时
random_offset = random.randint(-300, 300)  # -5 到 +5 分钟
redis.setex(cache_key, base_ttl + random_offset, data)
```
效果：大量 Key 的过期时间分散，不会在同一时刻集体失效。
2. 方案二：使用 Redis 集群
多节点部署，单个节点故障不影响整体缓存服务。
3. 方案三：设置多级缓存
```text
本地缓存(Caffeine/Guava)→ 分布式缓存(Redis)→ 数据库
```
本地缓存作为 Redis 的备份，即使 Redis 完全不可用，部分请求仍可由本地缓存服务。
4. 方案四：接口限流与熔断
```text
使用 Sentinel、Hystrix 等组件，对数据库访问进行限流，保护数据库不被冲垮。
```
### 4.2 缓存穿透(Cache Penetration)
#### 4.2.1 基本概念
缓存穿透是指请求的数据在缓存和数据库中都不存在，每次请求都直接打到数据库，导致数据库压力过大。
生活比喻：缓存穿透就像“查无此人的身份证号”。
- 你拿着一个不存在的身份证号去派出所查询(查询缓存和数据库都不存在的数据)
- 每次查询都要翻阅全部户籍档案(每次都查数据库)
- 恶意请求用大量不存在的 ID 攻击，导致派出所档案室(数据库)瘫痪
#### 4.2.2 原因分析
|原因|说明|
|---|---|
|恶意攻击|用大量不存在的 Key 发起请求|
|业务 Bug|查询条件错误，产生大量无效查询|
|数据被删除|缓存和数据库中的数据已被删除，但仍有请求查询|
#### 4.2.3 解决方案
1. 方案一：缓存空值
```python
def get_user(user_id):
    cache_key = f"user:{user_id}"
    user_data = redis.get(cache_key)
    
    if user_data is not None:
        # 注意：缓存中存的是 None 或空字符串，表示“数据不存在”
        return None if user_data == "" else user_data
    
    # 查询数据库
    user_data = db.query("SELECT * FROM users WHERE id = ?", user_id)
    
    if user_data:
        redis.setex(cache_key, 3600, user_data)
    else:
        # 数据不存在，缓存空值(过期时间短一些)
        redis.setex(cache_key, 60, "")  # 60 秒后重试
    
    return user_data
```
2. 方案二：布隆过滤器(Bloom Filter)
布隆过滤器是一种高效的数据结构，可以快速判断一个元素是否在集合中。
```text
请求到来 → 检查布隆过滤器 → 不存在 → 直接返回(不查数据库)
                          → 存在 → 查缓存 → 查数据库
```

|特性|说明|
|---|---|
|空间效率|极高，1 亿数据只需约 120 MB|
|查询速度|极快，O(k) 时间复杂度|
|特征|判断“不存在”是准确的，“存在”可能误判|
```python
# 伪代码示例
def is_user_exists(user_id):
    # 布隆过滤器判断
    if not bloom_filter.check(f"user:{user_id}"):
        return None  # 一定不存在，直接返回
    
    # 可能存在，查缓存
    user_data = redis.get(f"user:{user_id}")
    if user_data:
        return user_data
    
    # 查数据库
    user_data = db.query("SELECT * FROM users WHERE id = ?", user_id)
    return user_data
```
### 4.3 缓存击穿(Cache Breakdown)
#### 4.3.1 基本概念
缓存击穿是指某个热点 Key 在缓存失效的瞬间，大量并发请求同时查询该 Key，全部穿透到数据库。
生活比喻：缓存击穿就像“热门演唱会门票开售”。
- 某明星演唱会门票(热点数据)在 12:00 开售(缓存失效)
- 上万人同时抢购(大量并发请求)
- 售票系统(数据库)瞬间压力爆表
#### 4.3.3 解决方案
1. 方案一：互斥锁(Mutex)
```python
import threading

def get_hot_data(key):
    data = redis.get(key)
    if data:
        return data
    
    # 尝试获取锁
    lock_key = f"lock:{key}"
    if redis.setnx(lock_key, "1"):
        # 成功获取锁，查询数据库
        redis.expire(lock_key, 10)  # 设置锁超时
        data = db.query("SELECT * FROM hot_data WHERE id = ?", key)
        redis.setex(key, 3600, data)
        redis.delete(lock_key)  # 释放锁
        return data
    else:
        # 未获取到锁，等待并重试
        time.sleep(0.05)  # 等待 50ms
        return get_hot_data(key)  # 递归重试
```
2. 方案二：热点数据永不过期
```python
# 不设置过期时间，由后台线程定时刷新
redis.set("hot_product", product_data)  # 永不过期

# 后台线程每 5 分钟刷新一次
def refresh_cache():
    while True:
        time.sleep(300)
        product_data = db.query("SELECT * FROM hot_product")
        redis.set("hot_product", product_data)
```
3. 方案三：逻辑过期
```python
# 缓存中存储数据 + 过期时间戳
data = {
    "value": product_data,
    "expire_time": current_time + 3600  # 逻辑过期时间
}
redis.set("hot_product", json.dumps(data))

# 读取时：
raw_data = redis.get("hot_product")
if raw_data:
    data = json.loads(raw_data)
    if data["expire_time"] > current_time:
        return data["value"]  # 未过期，直接返回
    
    # 已过期，但先返回旧数据，异步刷新
    async_refresh_cache()  # 后台异步刷新
    return data["value"]   # 返回旧数据
```

## 五、缓存预热
### 5.1 基本概念
缓存预热是指在系统启动或上线前，提前将热点数据加载到缓存中，避免系统启动后大量请求穿透到数据库。
生活比喻：缓存预热就像“餐厅开张前的备菜”。
- 餐厅早上 10 点开门，但厨师 8 点就开始准备食材、提前煮好汤底(缓存预热)
- 第一批客人 10:30 到店，可以立即上菜(缓存命中)
- 而不是客人点菜后才开始洗菜切菜(避免数据库压力)
### 5.2 预热策略
1. 方案一：系统启动时自动预热
```python
def preheat_cache():
    # 预加载热门商品(前 100 个)
    hot_products = db.query("SELECT id FROM products ORDER BY view_count DESC LIMIT 100")
    for product in hot_products:
        product_data = db.query("SELECT * FROM products WHERE id = ?", product.id)
        redis.setex(f"product:{product.id}", 3600, product_data)
```
2. 方案二：脚本手动预热
```bash
# 使用 redis-cli 批量预热
cat product_ids.txt | while read id; do
    # 从数据库加载数据并写入 Redis
    # 这里需要结合业务逻辑实现
    echo "Loading product: $id"
done
```
3. 方案三：定时任务预热
```bash
# 每天凌晨 2 点执行预热任务
0 2 * * * /usr/local/bin/redis_preheat.sh
```

|---|---|---|

|热门商品列表|成交量/浏览量最高|高|
|公共配置数据|系统级配置|中|
|用户 Session|活跃用户|中|

## 六、生产环境最佳实践
### 6.1 缓存 Key 设计规范
|规范|示例|说明|
|---|---|---|
|业务名:对象名:ID|`user:profile:1001`|清晰标识业务和对象|
|使用冒号分隔|`order:detail:20240801`|便于在 Redis 中按前缀查询|
|控制 Key 长度|不超过 50 字符|节省内存|
|避免特殊字符|不使用空格和中文|避免编码问题|
|统一命名|团队内部统一|便于维护|
### 6.2 缓存过期时间设置建议
|数据类型|建议 TTL|说明|
|---|---|---|
|用户信息|1-6 小时|变更频率低|
|商品详情|1-24 小时|变更频率中等|
|配置数据|12-24 小时|变更频率低|
|热点数据|永不过期 + 定时刷新|保证可用性|
|Session|30 分钟|根据业务需求|
### 6.3 缓存监控指标
| 监控项       | 告警条件   | 说明             |
| --------- | ------ | -------------- |
| 缓存命中率     | 低于 80% | 缓存效果不佳         |
| 内存使用率     | 超过 80% | 即将达到 maxmemory |
| 缓存 Key 数量 | 异常增长   | 可能存在内存泄漏       |
| 慢查询数量     | 超过阈值   | 需要优化数据结构       |
### 6.4 常见陷阱与避免
| 陷阱        | 问题                        | 避免方案           |
| --------- | ------------------------- | -------------- |
| 缓存大 Key   | 单个 Key 值过大(> 1MB)，影响网络和内存 | 压缩数据，拆分为多个 Key |
| 缓存 Key 过多 | 无效缓存占用内存                  | 设置合理 TTL，定期清理  |
| 缓存雪崩      | 大量 Key 同时过期               | 过期时间加随机值       |
| 缓存穿透      | 大量不存在的数据查询                | 布隆过滤器 + 缓存空值   |
| 缓存击穿      | 热点 Key 失效瞬间               | 互斥锁 + 永不过期     |

## 七、总结
### 7.1 核心要点
1. Cache-Aside 是最常用的缓存模式，适合大多数业务场景
2. 缓存与数据库一致性是核心问题，建议采用“先更新数据库，再删除缓存”策略
3. 延迟双删可以解决并发更新时的脏数据问题
4. 订阅 Binlog 适合微服务架构，实现缓存与数据库解耦
5. 缓存雪崩、穿透、击穿是三大异常场景，各有成熟的应对方案
6. 缓存预热在系统启动时加载热点数据，避免启动冲击
### 7.2 模式选择建议
| 场景                  | 推荐模式                         | 理由        |
| ------------------- | ---------------------------- | --------- |
| 大多数业务(用户信息、商品详情等)   | Cache-Aside                  | 实现简单，应用广泛 |
| 使用 Spring Cache 的应用 | Read-Through / Write-Through | 框架天然支持    |
| 日志收集、高并发写入          | Write-Behind                 | 写入性能高     |
| 微服务架构               | Cache-Aside + Binlog 订阅      | 解耦、自动更新   |
缓存设计核心原则：
1. 读多写少的数据才需要缓存
2. 缓存不是万能的，需要配合数据库使用
3. 缓存的一致性是设计重点
4. 设置合理的过期时间，避免内存浪费
5. 监控缓存命中率，持续优化
