## 一、Redis 持久化概念
### 1.1 基本概念
Redis 的数据默认存储在内存中，这意味着一旦服务器进程退出或断电，数据就会全部丢失。为了解决这个问题，Redis 提供了持久化(Persistence)功能，能够定期把内存中的数据写入到磁盘文件中，当 Redis 重启时，再从磁盘文件恢复数据。
### 1.2 持久化的作用
1. 数据恢复，Redis 重启或崩溃后，通过持久化文件恢复数据，避免丢失
2. 灾难备份，持久化文件可作为备份，用于灾难恢复场景
3. 数据迁移，通过复制持久化文件，实现 Redis 实例间的数据迁移
4. 集群同步，主从复制中，从节点依赖持久化文件进行初始数据同步
持久化是 Redis 区别于纯内存缓存(如 Memcached)的关键特性，也是 Redis 能在生产环境中广泛应用的重要保障。
### 1.3 持久化方式
Redis 提供了三种主要的持久化方式：
1. RDB (Redis DataBase)
- 定期生成数据快照(全量备份)，将内存中的数据集快照(Snapshot)写入磁盘。
- 适合场景追求性能、可容忍少量数据丢失。

2. AOF (Append Only File)
- 记录每一条写命令(增量日志)，重启时重新执行所有命令来恢复数据。
- 追求数据安全、要求最少丢失

3. RDB + AOF
- 两者同时开启(混合持久化)，生产环境首选。

简单理解：
- RDB = 定期拍一张“全家福”照片
- AOF = 每天写“日记”，记录发生的每一件事
- 混合模式 = 既有全家福，又有日记，恢复最快、最全

## 二、RDB 持久化
### 2.1 基本概念
RDB(Redis Database)是 Redis 默认的持久化方式，通过在指定时间间隔对内存数据生成一份完整的快照(Snapshot)，并保存到磁盘文件中。

默认文件名是 dump.rdb，保存位置由 dir 配置项指定。

生活比喻：RDB 就像给整个数据库拍了一张“全家福”照片。你每隔一段时间拍一张，照片记录了那一刻所有人的样子。如果发生意外，你可以用最近的一张照片来还原。但两次拍照之间发生的事情，照片上是没有的。
### 2.2 工作原理
RDB 的工作流程如下：
1. 触发条件满足(自动或手动)
2. Redis 主进程 fork 出一个子进程(利用操作系统的写时复制机制)
3. 子进程负责将内存数据写入临时 RDB 文件
4. 写入完成后，用临时文件替换旧的 RDB 文件
5. 子进程退出，释放资源
写时复制(Copy-on-Write)机制：fork 操作会创建主进程的内存副本，但不会立即复制所有内存数据。只有当主进程修改数据时，才会复制该数据页。这样既保证了子进程能读取到 fork 时刻的完整数据，又减少了内存占用，提高了快照生成效率。
### 2.3 触发方式
RDB 快照的生成有两种触发方式：自动触发和手动触发。
#### 2.3.1 自动触发
通过配置文件中的 save 指令定义触发条件：
```conf
# 格式：save <秒数> <修改次数>
# 含义：在指定秒数内发生至少指定次数的数据修改，则自动触发 RDB

save 900 1     # 900 秒(15 分钟)内至少 1 个键被修改
save 300 10    # 300 秒(5 分钟)内至少 10 个键被修改
save 60 10000  # 60 秒(1 分钟)内至少 10000 个键被修改
```
其他自动触发场景：
- 执行 `shutdown` 命令且未开启 AOF 时，Redis 会自动生成 RDB 文件
- 主从复制时，主节点会生成 RDB 文件发送给从节点
#### 2.3.2 手动触发
| 命令       | 说明                               | 生产环境建议 |
| -------- | -------------------------------- | ------ |
| `SAVE`   | 同步操作，主进程直接生成 RDB，期间阻塞所有客户端请求     | 生产环境禁用 |
| `BGSAVE` | 异步操作，主进程 fork 子进程生成 RDB，不阻塞客户端请求 | 生产环境推荐 |

**示例**：
```text
127.0.0.1:6379> BGSAVE
Background saving started

127.0.0.1:6379> LASTSAVE
(integer) 1725000000    # 返回最后一次成功保存的时间戳
```
### 2.4 配置参数
| 配置项              | 默认值         | 说明                           |
| ---------------- | ----------- | ---------------------------- |
| `dbfilename`     | `dump.rdb ` | RDB 文件名                      |
| `dir`            | `./ `       | RDB 文件存储路径                   |
| `rdbcompression` | `yes`       | 是否压缩 RDB 文件(节省磁盘，但增加 CPU 开销) |
| `rdbchecksum`    | `yes `      | 是否对 RDB 文件进行校验(确保文件完整性)      |

**说明：** RDB 文件存储路径在生产环境中经常是/var/lib/redis。

### 2.5 RDB 的优点
1. 文件紧凑，适合备份
RDB 是一个非常紧凑的单文件，代表了 Redis 数据在某个时间点的完整状态。非常适合做备份—你可以每小时归档一次最近 24 小时的 RDB 文件，每天保存一份 30 天的快照。
2. 适合灾难恢复
RDB 是单个紧凑文件，可以轻松传输到远程数据中心或云存储(如 AWS S3)。
3. 对性能影响小
Redis 父进程唯一需要做的工作就是 fork 一个子进程，所有磁盘 I/O 都由子进程完成，父进程从不执行磁盘 I/O。
4. 恢复速度快
与 AOF 相比，RDB 允许更快地重启大型数据集。
### 2.6 RDB 的缺点
1. 可能丢失数据
RDB 是定期生成的快照，两次快照之间的数据不会保存。如果 Redis 在两次快照之间意外宕机，最近几分钟的数据就会丢失。
2. fork 操作可能耗时
如果数据集很大，fork() 操作可能会很耗时，导致 Redis 停止服务客户端几毫秒甚至一秒钟。
3. 大内存实例需预留内存
fork 子进程时需要额外内存(写时复制机制)，建议为 RDB 的 fork 预留至少 30% 的内存余量，否则可能因内存不足导致进程被杀死(OOM)。

## 三、AOF 持久化
### 3.1 基本概念
AOF(Append Only File)持久化记录服务器接收到的每一个写操作命令(如 SET、HSET、LPUSH 等)，并将这些命令追加到日志文件中。当 Redis 重启时，会重新执行 AOF 文件中的所有命令来恢复数据。

默认文件名是 appendonly.aof。

生活比喻：AOF 就像写“日记”。每做一件事(每执行一条写命令)，就在日记本上记一笔。如果出了意外，只要把日记从头到尾重新做一遍，就能恢复到出事前的状态。
### 3.2 工作原理
AOF 的工作主要分为三个步骤：命令追加、文件写入、文件同步。
1. 命令追加
当 Redis 执行完一个写命令后，会将该命令以 Redis 协议的格式追加到内存中的 AOF 缓冲区(aof_buf)末尾。
2. 文件写入和同步
AOF 缓冲区的内容需要写入到磁盘上的 AOF 文件。这里涉及两个系统调用：
- `write()`：将数据写入文件的内核缓冲区(page cache)，不是真正的落盘。
- `fsync()` (或 `fdatasync()`)：强制将内核缓冲区数据写入到磁盘。
Redis 通过配置项 `appendfsync` 来控制 `fsync` 的频率，从而平衡性能与数据安全。
### 3.3 同步策略(fsync)
AOF 的核心配置是 appendfsync，它决定了何时将数据从内存缓冲区真正写入磁盘。

|策略|说明|性能|安全性|
|---|---|---|---|
| always |每次写操作都立即写入磁盘|最差|最高(最多丢一条命令)|
| everysec |每秒写入一次(默认)|较好|较高(最多丢 1 秒数据)|
| no |由操作系统决定何时写入|最好|最差(可能丢大量数据)|

生产环境推荐使用 everysec，兼顾性能与安全，这也是 Redis 的默认值(如果开启 AOF)。
### 3.4 AOF 的重写机制
#### 3.4.1 重写作用
随着时间推移，AOF 文件会越来越大。比如你对同一个 Key 做了 100 次修改，AOF 里就记录了 100 条命令，但恢复时只需要最后一条命令的结果。

AOF 重写就是解决这个问题的：Redis 在后台生成一个新的 AOF 文件，只包含恢复当前数据集所需的最少操作命令，然后替换掉旧的 AOF 文件。
#### 3.4.2 重写原理
1. Redis 主进程 fork 出一个子进程。
2. 子进程读取当前内存中的数据，将其转换为一系列写命令，写入一个新的 AOF 文件(临时文件)。
3. 在此期间，主进程仍然处理客户端写请求，这些新命令会同时追加到旧的 AOF 文件和重写缓冲区中。
4. 子进程完成新 AOF 文件的生成后，通知主进程。
5. 主进程将重写缓冲区中的命令追加到新 AOF 文件的末尾，保证数据同步。
6. 最后用新文件原子地替换掉旧 AOF 文件。

这个过程既保证了 AOF 重写不会阻塞服务，又保证了重写过程中新增的数据不丢失。
#### 3.4.3 重写的触发方式
1. 自动触发条件通过

主要通过两个配置来控制
```conf
auto-aof-rewrite-percentage 100   # 当前 AOF 文件比上次重写后增长 100% 时触发
auto-aof-rewrite-min-size 64mb    # AOF 文件至少达到 64MB 才触发重写
```
**说明：** 当前 AOF 文件大小比上次重写后的大小增长了 100%(即翻了一倍)，且文件大小至少为 64 MB 时，自动触发 BGREWRITEAOF。

2. 手动触发

后台启动一个子进程来重写 AOF 文件，类似 `BGSAVE`，不阻塞主进程。
```text
127.0.0.1:6379> BGREWRITEAOF
Background append only file rewriting started
```
### 3.5 配置参数
| 配置项                           | 默认值              | 说明                                   |
| ----------------------------- | ---------------- | ------------------------------------ |
| `appendonly`                  | `no`             | 是否开启 AOF(生产环境建议 `yes`)               |
| `appendfilename`              | `appendonly.aof` | AOF 文件名                              |
| `appendfsync`                 | `everysec`       | 同步策略                                 |
| `auto-aof-rewrite-percentage` | `100`            | AOF 重写触发百分比                          |
| `auto-aof-rewrite-min-size`   | `64mb`           | AOF 重写触发最小文件大小                       |
| `no-appendfsync-on-rewrite`   | `no`             | 重写时是否禁止 fsync(`yes` 可降低阻塞，但增加数据丢失风险) |

当 AOF 重写正在执行时，如果 `appendfsync` 设置为 `always` 或 `everysec`，可能会因为磁盘繁忙导致主进程 `fsync` 被阻塞。可以设置：
```conf
no-appendfsync-on-rewrite yes
```
这样在重写期间，主进程不再执行 `fsync`，避免阻塞。缺点是一旦服务器崩溃，最后一次同步后到重写结束期间的数据可能丢失。一般可以接受，因为重写过程通常很快。
### 3.6 AOF 的优点
1. 数据安全性更高
使用默认的 everysec 策略，最多只丢失 1 秒的写入数据。
2. 日志是追加写入的
AOF 是追加写入，不会有寻道操作，断电时也不容易出现文件损坏。
3. 可读性强
AOF 文件是文本格式，包含了所有操作日志，易于理解和解析。
4. 可自动修复
即使 AOF 文件因磁盘满等原因写了一半，redis-check-aof 工具也能轻松修复。
### 3.7 AOF 的缺点
1. 文件体积大
AOF 文件是文本格式，体积通常是 RDB 文件的 3 到 5 倍。
2. 恢复速度慢
Redis 重启时需要逐条执行 AOF 中的所有命令，恢复速度比 RDB 慢得多。
3. 对性能有影响
开启 AOF 后，每次写操作都需要追加到文件，对性能有一定影响。always 策略影响最大，everysec 影响较小。

## 四、RDB + AOF 持久化
### 4.1 基本概念
为了解决 AOF 恢复慢、RDB 数据安全性低的问题，Redis 4.0 引入了混合持久化，同时开启 RDB 和 AOF，将两者的优势结合起来。

在混合持久化模式下：
- RDB 负责定期生成快照，用于快速恢复和备份归档
- AOF 负责记录增量写命令，用于数据安全保障
- AOF 重写时，会将 RDB 快照嵌入 AOF 文件的头部

生活比喻：混合持久化 = 全家福 + 日记。
- 每个月初拍一张全家福(RDB 快照)
- 每天写日记记录每天发生的事(AOF 增量日志)
- 恢复时：先看全家福知道月初的样子，再翻日记知道之后的变化
- 比只看日记(纯 AOF)恢复快得多，比只看全家福(纯 RDB)数据更全
### 4.2 配置方式
在 Redis 7.2.x 中开启混合持久化(redis.conf)：
```conf
# 开启 RDB(默认已开启)
save 900 1
save 300 10
save 60 10000

# 开启 AOF
appendonly yes
appendfsync everysec

# 开启混合持久化(关键配置)
aof-use-rdb-preamble yes

# AOF 重写配置
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# RDB 配置
dbfilename dump.rdb
dir /var/lib/redis
rdbcompression yes
rdbchecksum yes

# AOF 配置
appendfilename "appendonly.aof"
```
关键配置说明：
- appendonly yes：开启 AOF
- aof-use-rdb-preamble yes：开启混合持久化，AOF 重写时在文件头部嵌入 RDB 快照
### 4.3 恢复顺序
当同时开启 RDB 和 AOF 时，Redis 重启会优先使用 AOF 文件恢复数据，因为 AOF 通常保存了比 RDB 更完整的数据。
在混合持久化模式下，AOF 文件头部是 RDB 快照，后面是增量 AOF 命令。恢复时：
- 先快速加载 AOF 头部的 RDB 快照
- 再回放后面的增量 AOF 命令
- 既快又全
### 4.4 混合持久化优点

| 对比维度  | 纯 RDB       | 纯 AOF      | 混合持久化            |
| ----- | ----------- | ---------- | ---------------- |
| 数据安全性 | 低(可能丢几分钟数据) | 高(最多丢 1 秒) | 高(最多丢 1 秒)       |
| 恢复速度  | 快           | 慢          | 快(RDB 快照 + 少量增量) |
| 文件大小  | 小           | 大          | 较小(RDB 二进制 + 增量) |
| 备份便利性 | 方便(单文件)     | 一般         | 方便(AOF 单文件含 RDB) |

## 五、生产环境参考配置
### 5.1 三种场景的配置模板
#### 5.1.1 缓存型场景
适用于纯缓存场景，数据丢失后可从数据库重建。
```conf
# 关闭 RDB(注释掉所有 save 规则)
# save 900 1
# save 300 10
# save 60 10000

# 关闭 AOF
appendonly no
```
注意：如需备份，可在从节点定时执行 BGSAVE，避免影响主节点性能。
#### 5.1.2 通用生产场景
适用于大多数业务(社交、电商等)场景，兼顾性能与数据安全。
```conf
# RDB 配置
save 900 1
save 300 10
save 60 10000
dbfilename dump.rdb
rdbcompression yes
rdbchecksum yes

# AOF 配置
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec

# 混合持久化
aof-use-rdb-preamble yes

# AOF 重写
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# 数据目录
dir /var/lib/redis
```
#### 5.1.3 强一致型场景
适用于金融、订单等对数据一致性要求极高的场景。
```conf
# AOF 配置
appendonly yes
appendfsync always    # 每次写都落盘，安全性最高
aof-use-rdb-preamble yes

# RDB 仍建议开启，利于重写与恢复
save 900 1
save 300 10
save 60 10000
```
注意：appendfsync always 会显著降低写性能，仅在确实需要强一致的场景使用。
### 5.2 配置参数速查表
| 配置项                           | 缓存型  | 通用型(推荐)                         | 强一致型                            | 说明           |
| ----------------------------- | ---- | ------------------------------- | ------------------------------- | ------------ |
| `save`                        | 注释掉  | `900 1` / `300 10` / `60 10000` | `900 1` / `300 10` / `60 10000` | RDB 触发条件     |
| `appendonly`                  | `no` | `yes`                           | `yes`                           | 是否开启 AOF     |
| `appendfsync`                 | -    | `everysec`                      | `always`                        | AOF 同步策略     |
| `aof-use-rdb-preamble`        | -    | `yes`                           | `yes`                           | 混合持久化        |
| `auto-aof-rewrite-min-size`   | -    | `64mb`                          | `64mb`                          | AOF 重写最小文件大小 |
| `auto-aof-rewrite-percentage` | -    | `100`                           | `100`                           | AOF 重写增长百分比  |
### 5.3 生产环境注意事项
1. 避免在高峰期执行 BGSAVE
在业务高峰期执行 BGSAVE 可能因 fork 操作消耗资源而影响服务。建议在低峰期进行手动备份。
2. 为 fork 预留内存
大内存实例执行 BGSAVE 或 BGREWRITEAOF 时会 fork 子进程，需要额外内存。建议为 Redis 预留 至少 30% 的内存余量。
3. 监控持久化状态
使用 INFO persistence 命令监控持久化状态：
- aof_enabled：AOF 是否开启
- aof_rewrite_in_progress：AOF 重写是否正在进行
- last_bgrewrite_status：最后一次 AOF 重写的状态
- rdb_last_bgsave_status：最后一次 RDB 保存的状态
- 设置告警：当 `rdb_last_bgsave_time_sec` ，该值超过 10 秒时需关注，超过 30 秒时需告警(具体阈值可根据实例内存大小调整)。
4. 避免内存不足导致 swap
避免在物理内存不足的机器上运行 Redis，防止内存交换(swap)操作导致性能骤降。
5. 务必开启持久化
    即使你使用 Redis 只作为缓存，也建议至少开启 RDB(例如 `save 3600 1`)，否则一旦重启，所有缓存数据瞬间丢失，可能引发“缓存雪崩”。
6. 生产环境推荐组合
    - 开启 AOF，设置 `appendfsync everysec`。
    - 开启混合持久化 `aof-use-rdb-preamble yes`。
    - 同时配置 RDB 自动条件(如 `save 900 1`)，作为双重保障。
    - 这样即使 AOF 文件损坏，你还有 RDB 兜底。
7. 定期备份持久化文件到远程
    使用 `cp`、`rsync` 或云存储，将 `dump.rdb` 和 `appendonly.aof` 备份到其他机器。恢复时，直接替换文件并重启 Redis。
8. 合理配置重写触发条件
    - 对于 AOF 自动重写，`auto-aof-rewrite-min-size` 不要太小，避免频繁重写。
    - 建议至少 `64mb` 或 `256mb`，百分比保持 `100`。
9. 避免在内存压力大的机器上同时执行 BGSAVE / BGREWRITEAOF
    因为 fork 需要复制页表，内存越大耗时越久。如果内存 > 10 GB，建议在业务低峰期手动执行，或使用主从节点错开执行。
10. 持久化文件存放路径的隔离
生产环境建议将 RDB 和 AOF 文件放在不同磁盘或不同挂载点，避免同一磁盘故障导致两种持久化文件同时损坏。
11. AOF 文件过大导致磁盘写满的风险
当 AOF 重写未及时触发或磁盘空间不足时，AOF 文件可能持续增长并写满磁盘，导致 Redis 无法正常写入。需监控磁盘使用率，并合理配置重写触发条件。

## 六、故障恢复与文件维护
### 6.1 恢复数据
当 Redis 重启时，数据恢复的优先级如下：
- 如果 AOF 开启：优先加载 AOF 文件恢复数据
- 如果 AOF 未开启：加载 RDB 文件恢复数据
 当 AOF 文件损坏且无法修复时，可临时改用 RDB 文件恢复(需将 `appendonly` 临时设为 `no` 再重启)。此操作有风险，非紧急情况不建议执行。
### 6.2 AOF 文件损坏修复
如果 AOF 文件损坏，可以使用修复工具：
```bash
redis-check-aof --fix appendonly.aof
```
### 6.3 RDB 文件校验
RDB 文件可以通过配置开启校验：
```conf
rdbchecksum yes
```
开启后，Redis 加载 RDB 文件时会校验文件完整性，防止因文件损坏导致加载错误数据。

## 七、总结
持久化是 Redis 从“缓存”走向“可靠数据库”的关键特性。RDB 适合备份和快速恢复，AOF 适合近实时安全，混合持久化则结合了两者优点。根据你的业务场景选择合适的策略，并遵循最佳实践，就能充分发挥 Redis 的高性能同时保障数据安全。
