## 一、备份数据卷作用
### 1.1 容器的无状态特性
Docker 容器的设计哲学是 “无状态” 。容器本身是临时的、可替换的，容器删除后，容器内部的所有数据都会丢失。

|容器存储类型|生命周期|数据持久性|
|---|---|---|
|容器可写层|随容器删除而消失|❌ 不持久|
|绑定挂载(Bind Mount)|独立于容器，但依赖宿主机目录|✅ 持久(需手动管理)|
|数据卷(Volume)|独立于容器，由 Docker 管理|✅ 持久(需备份)|

数据卷虽然是持久化的，但它并非“永远安全” ，仍然面临以下风险：

|风险|说明|
|---|---|
|磁盘故障|宿主机硬盘损坏，所有数据丢失|
|误删除|执行 `docker volume rm` 或 `docker compose down -v` 误删数据|
|人为错误|运维人员误操作覆盖了数据库数据|
|勒索病毒|服务器被入侵，数据被加密或删除|
|容器应用 Bug|应用逻辑错误导致数据被破坏|

核心原则：数据卷是持久化的，但不是“永久安全”的。备份是数据安全的最后一道防线。
### 1.2 备份的核心思路
备份 Docker 数据卷的本质是：将数据卷中的文件复制到安全位置(另一个目录、另一台机器、云存储) 。
```text
数据卷(/var/lib/docker/volumes/xxx/_data)
              ↓
         备份操作
              ↓
    安全存储位置(/backup/、NFS、云盘)
```

## 二、备份前的准备工作

### 2.1 查看当前数据卷
在执行备份之前，需要先了解当前系统中有哪些数据卷，以及它们被哪些容器使用。
```bash
# 列出所有数据卷
docker volume ls

# 查看数据卷详情(包含挂载点路径)
docker volume inspect 数据卷名
```
命令解释：
- `docker volume ls`：列出所有数据卷，显示卷名和驱动类型。
- `docker volume inspect 卷名`：查看数据卷的详细信息，其中 `Mountpoint` 字段表示数据在宿主机上的实际存储路径。
查看容器与数据卷的关联：
```bash
# 查看某个容器挂载了哪些数据卷
`docker inspect 容器名 --format='{.Mounts}'`
```
命令解释：
- `docker inspect 容器名 --format='{.Mounts}'`：显示容器挂载的所有数据卷和绑定挂载的详细信息，包括类型、源路径和目标路径。
### 2.2 查看数据卷的实际大小

在备份前了解数据量大小，有助于选择合适的备份方式和存储位置。

```bash
# 查看数据卷的实际大小(需进入宿主机目录)
sudo du -sh /var/lib/docker/volumes/数据卷名/_data

# 或使用 docker system df 查看整体磁盘使用
docker system df
```
命令解释：
- `du -sh /path`：显示指定路径的总大小(`-s` 汇总，`-h` 人类可读格式)。
- `docker system df`：显示 Docker 整体磁盘使用情况，包括镜像、容器、数据卷、构建缓存分别占用的空间。

### 2.3 确定备份策略
| 策略   | 说明               | 适用场景          |
| ---- | ---------------- | ------------- |
| 完全备份 | 每次备份所有数据         | 数据量小、变化少的场景   |
| 增量备份 | 只备份自上次备份以来变化的数据  | 数据量大、变化频繁的场景  |
| 定期备份 | 按固定时间间隔(如每天凌晨)执行 | 生产环境推荐        |
| 实时备份 | 每次数据变化时立即备份      | 对数据丢失容忍度极低的场景 |

## 三、数据卷备份
### 3.1 使用临时容器打包备份
这是最通用的数据卷备份方法，适用于所有类型的数据卷，无论是命名卷还是匿名卷。

核心思路：启动一个临时容器，同时挂载要备份的数据卷和一个备份目标目录，使用 tar 命令将数据卷内容打包压缩。
```bash
docker run --rm \
  -v 要备份的数据卷名:/source:ro \
  -v /宿主机备份目录:/backup \
  alpine \
  tar czf /backup/备份文件名.tar.gz -C /source .
```
命令解释：

| 参数 | 说明 |
|------|------|
| `--rm` | 容器执行完成后自动删除，不留痕迹 |
| `-v 卷名:/source:ro` | 将数据卷挂载到容器的 `/source` 目录，`ro` 表示只读，防止备份过程中意外修改数据 |
| `-v /backup:/backup` | 将宿主机备份目录挂载到容器的 `/backup` 目录 |
| `alpine` | 使用轻量级 Alpine 镜像(内含 `tar` 命令) |
| `tar czf /backup/xxx.tar.gz -C /source .` | 将 `/source` 目录下的所有文件打包压缩到 `/backup/xxx.tar.gz` |

完整示例：
```bash
# 1. 先查看有哪些数据卷需要备份
docker volume ls

# 2. 备份名为 myapp_db_data 的数据卷

docker run --rm \
  -v myapp_db_data:/source:ro \
  -v /data/backups:/backup \
  alpine \
  tar czf /backup/myapp_db_data_20260119.tar.gz -C /source .

# 3. 验证备份文件已生成

ls -lh /data/backups/
```

备份多个数据卷：
```bash
# 方式一：分别备份(推荐，恢复时更灵活)
docker run --rm -v volume1:/source:ro -v /backup:/backup alpine tar czf /backup/volume1.tar.gz -C /source .
docker run --rm -v volume2:/source:ro -v /backup:/backup alpine tar czf /backup/volume2.tar.gz -C /source .

# 方式二：使用脚本循环备份(适合多个卷)
for VOL in $(docker volume ls -q); do
  docker run --rm -v ${VOL}:/source:ro -v /backup:/backup alpine \
    tar czf /backup/${VOL}_$(date +%Y%m%d).tar.gz -C /source .
done
```
### 3.2 直接复制宿主机目录
如果知道数据卷在宿主机上的实际存储路径，也可以直接使用 `cp` 命令备份。
```bash
# 1. 查看数据卷的挂载点
docker volume inspect 数据卷名

# 输出示例: "Mountpoint": "/var/lib/docker/volumes/myapp_db_data/_data"

# 2. 直接复制数据目录
sudo cp -r /var/lib/docker/volumes/myapp_db_data/_data /backup/myapp_db_data_backup
```
命令解释：
- docker volume inspect：查看数据卷的元数据，其中 Mountpoint 是该卷在宿主机上的实际路径。
- sudo cp -r：递归复制整个目录(需要 root 权限，因为 /var/lib/docker/ 目录属于 root)。
注意事项：
- 如果容器正在运行且正在写入数据，直接复制可能导致备份不完整(复制过程中数据可能变化)。
- 建议在数据库容器备份前暂停写入或锁表。
- 对于生产环境的数据库，使用 `cp` 直接复制可能不是最安全的方式，建议使用专业的数据库备份工具。
### 3.2 使用 docker commit 
docker commit 可以将容器的当前状态保存为镜像，但不适合作为数据备份方案。
```bash
# 将容器保存为镜像(包含数据)
docker commit 容器名 备份镜像名:tag
```
为什么不推荐：

|问题|说明|
|---|---|
|镜像体积大|包含整个容器文件系统，不仅仅是数据|
|不方便增量备份|每次备份都是全量，无法只备份变化部分|
|不便恢复单文件|要从镜像中提取数据需要额外步骤|
|不适合数据库|运行中的数据库使用 commit 可能导致数据不一致|

## 四、绑定挂载(Bind Mount)的备份
### 4.1 绑定挂载概念
绑定挂载是将宿主机上的指定目录挂载到容器内部。它的数据存储在宿主机用户指定的路径，而不是 Docker 管理的 /var/lib/docker/volumes/。
```yaml
# docker-compose.yml 示例
services:
  web:
    image: nginx
    volumes:
      - /data/nginx/html:/usr/share/nginx/html
```
与数据卷的对比：

|对比维度|数据卷(Volume)|绑定挂载(Bind Mount)|
|---|---|---|
|宿主机存储路径| `/var/lib/docker/volumes/` |用户指定路径(如 `/data/nginx/`)|
|备份方式|临时容器 + tar|直接 `cp` 或 `rsync` |
|权限管理|Docker 自动处理|需手动处理 UID 和 SELinux|
### 4.2 绑定挂载的备份方法
绑定挂载的备份更直接，因为路径是用户已知的。
```bash
# 1. 查看容器挂载的绑定目录
`docker inspect 容器名 --format='{.Mounts}'`

# 2. 直接备份宿主机目录
sudo tar czf /backup/nginx_html_backup.tar.gz -C /data/nginx/html .

# 或使用 rsync(支持增量备份)
sudo rsync -av /data/nginx/html/ /backup/nginx_html/
```
命令解释：
- `docker inspect --format='{.Mounts}'`：查看容器的所有挂载点，可以从中找到绑定挂载的源路径。
- `tar czf ... -C /path .`：将指定路径下的所有文件打包压缩。
- `rsync -av`：同步目录内容，只复制变化的部分(增量备份)。
### 4.3 备份时需要注意的事项
|注意事项|说明|
|---|---|
|停止或暂停容器|对于数据库类应用，备份前最好暂停写入或停止容器|
|使用只读挂载|备份容器可以只读挂载数据卷，防止意外修改|
|校验备份完整性|备份后使用 `tar tvf` 或 `md5sum` 验证备份文件|
|压缩备份|使用 `tar -z` 压缩，节省存储空间|

## 五、数据恢复
### 5.1 从 tar 备份文件恢复到数据卷
这是最通用的数据恢复方法，与备份方法对称。

核心思路：启动一个临时容器，将数据卷挂载为目标路径，将备份 tar 文件解压到该目录中。
```bash
docker run --rm \
  -v 目标数据卷名:/target \
  -v /宿主机备份目录:/backup \
  alpine \
  tar xzf /backup/备份文件名.tar.gz -C /target
```
命令解释：

|参数|说明|
|---|---|
|`-v 目标数据卷名:/target`|将待恢复的数据卷挂载到容器的 `/target` 目录|
|`-v /backup:/backup`|将存放备份文件的宿主机目录挂载到容器的 `/backup`|
|`tar xzf /backup/xxx.tar.gz -C /target`|将备份文件解压到 `/target` 目录|

完整示例：
```bash
# 1. 如果数据卷不存在，先创建它
docker volume create myapp_db_data

# 2. 恢复数据
docker run --rm \
  -v myapp_db_data:/target \
  -v /data/backups:/backup \
  alpine \
  tar xzf /backup/myapp_db_data_20260119.tar.gz -C /target

# 3. 验证数据已恢复
docker run --rm -v myapp_db_data:/target alpine ls -la /target
```
### 5.2 恢复到已存在的容器
如果容器已经存在，但数据丢失或损坏，可以先停止容器，恢复数据卷，再重启容器。
```bash
# 1. 停止容器
docker stop 容器名

# 2. 恢复数据卷
docker run --rm -v 数据卷名:/target -v /backup:/backup alpine \
  tar xzf /backup/备份文件.tar.gz -C /target

# 3. 重启容器
docker start 容器名
```
### 5.3 恢复到新的数据卷
在数据迁移场景下，可以将数据恢复到新的数据卷，然后让新容器使用这个新卷。
```bash
# 1. 创建新的数据卷
docker volume create new_db_data

# 2. 将备份恢复到新卷
docker run --rm -v new_db_data:/target -v /backup:/backup alpine \
  tar xzf /backup/old_db_data_20260119.tar.gz -C /target

# 3. 启动新容器使用新卷
docker run -d --name new-app -v new_db_data:/var/lib/mysql mysql:5.7
```
### 5.4 恢复前的检查清单
|检查项|命令|说明|
|---|---|---|
|检查备份文件是否存在|`ls -lh /backup/备份文件名`|确保备份文件可访问|
|检查备份文件完整性|`tar tvf /backup/备份文件名 \| head -20`|测试 tar 文件是否损坏|
|确认目标数据卷名称|`docker volume ls`|避免恢复到错误的数据卷|
|确认目标容器已停止|`docker ps \| grep 容器名`|恢复前应停止使用该数据卷的容器|

## 六、自动化备份方案
### 6.1 编写备份脚本
将备份操作写成 Shell 脚本，便于定期执行。
```bash
#!/bin/bash
# /usr/local/bin/backup-volumes.sh

# 配置项
BACKUP_DIR="/data/backups"
RETENTION_DAYS=30
DATE=$(date +%Y%m%d_%H%M%S)

# 创建备份目录(如果不存在)
mkdir -p ${BACKUP_DIR}

# 需要备份的数据卷列表(按需修改)
VOLUMES=(
  "myapp_db_data"
  "myapp_redis_data"
  "myapp_uploads"
)

# 逐个备份
for VOL in "${VOLUMES[@]}"; do
  echo "[$(date)] 开始备份数据卷: ${VOL}"
  
  # 检查数据卷是否存在
  if docker volume inspect ${VOL} > /dev/null 2>&1; then
    docker run --rm \
      -v ${VOL}:/source:ro \
      -v ${BACKUP_DIR}:/backup \
      alpine \
      tar czf /backup/${VOL}_${DATE}.tar.gz -C /source .
    
    if [ $? -eq 0 ]; then
      echo "[$(date)] 备份成功: ${VOL}_${DATE}.tar.gz"
    else
      echo "[$(date)] 备份失败: ${VOL}"
    fi
  else
    echo "[$(date)] 数据卷不存在，跳过: ${VOL}"
  fi
done

# 清理超过保留天数的旧备份
echo "[$(date)] 清理 ${RETENTION_DAYS} 天前的备份文件"
find ${BACKUP_DIR} -name "*.tar.gz" -mtime +${RETENTION_DAYS} -delete

echo "[$(date)] 备份完成"
```
脚本解释：

|部分|说明|
|---|---|
| `BACKUP_DIR="/data/backups"` |备份文件存放目录(根据实际环境修改)|
| `RETENTION_DAYS=30` |备份保留天数，超过 30 天的自动删除|
| `VOLUMES=(...)` |需要备份的数据卷列表(按需添加或修改)|
| `docker volume inspect ${VOL} > /dev/null 2>&1` |检查数据卷是否存在，不输出任何信息|
| `find ... -mtime +${RETENTION_DAYS} -delete` |删除超过保留天数的备份文件|
### 6.2 配置定时任务(crontab)
使用 crontab 配置定时执行备份脚本。
```bash
# 编辑当前用户的 crontab
crontab -e

# 添加定时任务(每天凌晨 2:00 执行备份)
0 2 * * * /usr/local/bin/backup-volumes.sh >> /var/log/backup-volumes.log 2>&1
```
### 6.3 备份到远程存储
将备份文件同步到远程存储(NFS、云盘、对象存储)是生产环境的推荐做法。
1. 使用 rsync 同步到远程服务器：
```bash
# 在备份脚本末尾添加
rsync -av ${BACKUP_DIR}/ user@remote-server:/backup-storage/
```
命令解释：
- `rsync -av`：归档模式同步，保留文件属性，显示进度。
- `user@remote-server:/backup-storage/`：远程服务器地址和存储路径。

2. 使用 rclone 同步到云对象存储(如阿里云 OSS、腾讯云 COS)：
```bash
# 安装 rclone
sudo dnf install -y rclone

# 配置 rclone(交互式配置)
rclone config

# 同步到云存储
rclone sync /data/backups/ oss:my-bucket/backups/
```

## 七、数据库数据卷的特殊备份策略
### 7.1 MySQL / MariaDB
对于 MySQL 数据卷，不推荐直接打包 /var/lib/mysql 目录，因为：
- 运行中的 MySQL 有缓存和未落盘的数据，直接复制可能导致数据不一致。
- 复制过程中表可能被锁定，导致备份损坏。
推荐方案：使用 mysqldump 导出 SQL 文件，然后备份 SQL 文件。
```bash
# 使用 mysqldump 导出数据库
docker exec 容器名 mysqldump -u root -p密码 --all-databases > /backup/mysql_$(date +%Y%m%d).sql

# 或结合数据卷备份：先停止容器，再备份数据卷
docker stop 容器名
docker run --rm -v mysql_data:/source:ro -v /backup:/backup alpine \
  tar czf /backup/mysql_data_$(date +%Y%m%d).tar.gz -C /source .
docker start 容器名
```
推荐做法：
```bash
#!/bin/bash
# MySQL 专用备份脚本

CONTAINER_NAME="myapp-db"
BACKUP_DIR="/data/backups"
DATE=$(date +%Y%m%d_%H%M%S)

# 1. 使用 mysqldump 导出(一致性快照)
docker exec ${CONTAINER_NAME} mysqldump \
  --single-transaction \
  --routines \
  --triggers \
  --all-databases \
  > ${BACKUP_DIR}/mysql_dump_${DATE}.sql

# 2. 压缩 SQL 文件
gzip ${BACKUP_DIR}/mysql_dump_${DATE}.sql

echo "备份完成: mysql_dump_${DATE}.sql.gz"
```
### 7.2 PostgreSQL
PostgreSQL 使用 pg_dumpall 或 pg_dump 导出。
```bash
# 导出所有数据库
docker exec 容器名 pg_dumpall -U postgres > /backup/postgres_$(date +%Y%m%d).sql

# 或使用数据卷备份(需先停止容器)
docker stop 容器名
docker run --rm -v pg_data:/source:ro -v /backup:/backup alpine \
  tar czf /backup/pg_data_$(date +%Y%m%d).tar.gz -C /source .
docker start 容器名
```
### 7.3 Redis
Redis 数据卷备份相对简单，因为 Redis 会将数据持久化到 dump.rdb 或 appendonly.aof 文件。
```bash
# 在容器内执行 BGSAVE 生成 RDB 文件
docker exec 容器名 redis-cli BGSAVE

# 等待 BGSAVE 完成(检查日志)
docker exec 容器名 redis-cli LASTSAVE

# 备份数据卷
docker run --rm -v redis_data:/source:ro -v /backup:/backup alpine \
  tar czf /backup/redis_data_$(date +%Y%m%d).tar.gz -C /source .
```

## 八、总结
Docker 数据卷备份与恢复是生产环境运维的核心技能之一。
1. 备份的必要性：
    - 数据卷虽然是持久化的，但并非永久安全。
    - 磁盘故障、误删除、人为错误、勒索病毒都可能导致数据丢失。
2. 备份的核心思路：
    - 数据卷备份本质是将数据卷中的文件复制到安全位置。
    - 最通用的方法是使用临时容器 + `tar` 命令打包备份。
3. 备份方法：
    - 数据卷(Volume)：使用 `docker run --rm -v 卷名:/source:ro -v /backup:/backup alpine tar czf ...`
    - 绑定挂载(Bind Mount)：直接 `cp` 或 `rsync` 宿主机目录。
    - 数据库：使用专用工具(`mysqldump`、`pg_dumpall`)导出逻辑备份。
4. 恢复方法：
    - 恢复是备份的逆向操作：`tar xzf 备份文件.tar.gz -C /target`
    - 恢复前应停止使用该数据卷的容器。
5. 自动化备份：
    - 编写 Shell 脚本 + crontab 定时执行。
    - 设置备份保留策略(如保留 30 天)。
    - 将备份同步到远程存储(NFS、云盘、对象存储)。
	
6. 生产环境提醒
- 备份文件存储路径应避免放在 /var/lib/docker/ 目录下，以防 Docker 自身清理时误删。
- 生产环境至少同时保留本地备份和远程备份两份数据。
- 定期执行恢复演练，验证备份文件可用性。
- 备份脚本执行时应检查磁盘空间，避免因空间不足导致备份失败。

备份不是“做完就完了”的工作，而是需要持续验证和优化的流程。最重要的原则是：没有经过恢复验证的备份，等于没有备份。
