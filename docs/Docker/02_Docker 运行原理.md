## 一、容器概念
### 1.1 容器的本质
很多人把容器想象成一个“小虚拟机”，但这是一个常见的误解。容器的本质，就是宿主机上的一个普通进程，只不过这个进程被 Linux 内核“骗”了一下，让它以为自己独占了一整台机器。

打个比方：你在一栋大楼(宿主机)里上班，本来你和所有人共用走廊、电梯、茶水间。突然有一天，你走进一个房间，这个房间有自己的门牌号、自己的空调、自己的电话线，从房间里面往外看，你觉得自己独占了一整栋楼—但实际上，你仍然在同一栋楼里，和其他人共用着大楼的地基和承重墙。这就是容器的本质：共享内核，但拥有独立的视图。
### 1.2 运行原理作用
理解 Docker 的运行原理，不是为了背概念，而是为了在生产环境中能够：
- 排查容器启动失败、资源不足等问题；
- 合理配置容器的 CPU、内存等资源限制；
- 理解容器为什么启动这么快、为什么比虚拟机省资源；
- 在设计容器化方案时做出正确的架构决策。

总结： 容器 = 受隔离与资源限制的普通进程。

## 二、容器化的底层内核机制
Docker 之所以能实现容器的“隔离”“限流”“分层”三大能力，靠的是 Linux 内核自带的三种机制。Docker 本身并没有发明这些技术，它只是把这些底层能力包装成了好用的工具。
### 2.1 命名空间(Namespace)
命名空间(Namespace)是 Linux 内核提供的一种机制，它让一组进程看到一份独立的、被裁剪过的系统资源视图。简单说，就是让容器里的进程“以为”自己独占某些资源，实际上这些资源是和宿主机及其他容器共享的，实现"隔离“的效果。

Docker 主要使用以下七种命名空间：

| 命名空间类型 | 隔离对象      | 效果说明                              |
| ------ | --------- | --------------------------------- |
| PID    | 进程号       | 容器内进程从 PID 1 开始重新编号，看不到宿主机上的其他进程  |
| NET    | 网络栈       | 容器拥有独立的网卡、IP 地址、路由表、端口空间          |
| IPC    | 进程间通信     | 容器拥有独立的 System V IPC 和 POSIX 消息队列 |
| MNT    | 挂载点       | 容器拥有独立的文件系统挂载视图                   |
| UTS    | 主机名与域名    | 容器可以拥有自己的 hostname，与宿主机不同         |
| USER   | 用户与用户组 ID | 容器内的 root 可以映射为宿主机上的非特权用户         |
| Cgroup | cgroup 视图 | 容器拥有独立的 cgroup 层次结构视图(Linux 4.6+) |

如何验证：可以在 Rocky Linux 8 上启动一个容器，然后查看它在宿主机上的命名空间。
```bash
# 启动一个长期运行的容器
docker run -d --name demo alpine sleep 3600

# 找到容器内 sleep 进程在宿主机上的真实 PID
PID=$(docker inspect -f '{{.State.Pid}}' demo)

# 查看该进程所属的命名空间
ls -l /proc/$PID/ns/
```
你会看到类似 pid、net、mnt 等文件，每个文件都有一个唯一的编号，代表该进程所属的命名空间。不同容器的命名空间编号不同，说明它们彼此隔离。
### 2.2 控制组(Cgroup)
命名空间只是让容器“看不到”别人的资源，但从操作系统内核的视角来看，这些被隔离的进程和普通进程没有区别—它们仍然会抢 CPU、占内存。

控制组(Cgroup)的作用就是限制容器进程能够使用的系统资源上限，比如 CPU 时间片、内存使用量、磁盘 I/O 速率等，实现资源限制。

Cgroup 主要提供三种能力：
- 资源限制：设置容器能使用的 CPU、内存、磁盘 I/O 的上限；
- 优先级分配：为不同容器设置资源使用的优先级，实现服务质量(QoS)管理；
- 资源审计：监控容器的资源使用情况并生成报告。
生产环境示例：在 Rocky Linux 8 上运行容器时，可以通过参数限制资源使用。
```bash
# 限制容器最多使用 2 个 CPU 核心和 512MB 内存
docker run -d --cpus=2 --memory=512m --name web nginx
```
如果容器尝试使用超过 512MB 内存，会被内核强制终止(OOM Killer)，从而避免单个容器拖垮整台宿主机。
### 2.3 联合文件系统(UnionFS)
Docker 镜像之所以高效，核心在于联合文件系统(Union File System，UnionFS) 。

UnionFS 是一种分层、轻量级的文件系统，它允许将多个目录挂载到同一个目录下，对外提供一个统一的视图。也就是说，多个文件系统层可以“叠加”在一起，从外面看就像是一个完整的文件系统。

通俗理解：就像做三明治—面包片(基础层)、火腿(中间层)、生菜(上层)叠在一起，你看到的是一个完整的三明治，但实际上每一层都是独立的，可以单独替换。
### 2.4 容器的底层基石
Namespace、Cgroups 和 UnionFS 共同构成了容器的三大底层基石，三者缺一不可：
- Namespace 实现资源隔离，为容器进程提供独立的系统视图(PID、网络、用户等)，使其“看不见”宿主机及其他容器；
- Cgroups 实现资源限制，为容器精确分配 CPU、内存等硬件资源，使其“用不超”配额；
- UnionFS(联合文件系统) 实现存储驱动，通过分层镜像和写时复制(CoW)机制，使容器“装得省”(共享基础层)且“启得快”(无需完整 OS 拷贝)。

三者结合，最终为用户提供了一个 “隔离、受控、轻量” 的标准化运行环境—这就是容器。

## 三、Docker 的组件架构
Docker 采用客户端-服务器(C/S)架构。用户通过客户端向服务端(Docker 守护进程)发送请求，服务端完成所有工作后返回结果。
### 3.1 架构总览
Docker 的架构从用户输入命令到容器真正运行，大致经过以下链路：
```text
docker 命令(CLI) → dockerd(守护进程) → containerd → containerd-shim → runc
```
每一层都有明确的职责分工。
### 3.2 Docker 客户端(CLI)
Docker 客户端就是我们日常使用的 docker 命令。当你在终端输入 docker run nginx 时，客户端会将这个命令转换成 API 请求，发送给 Docker 守护进程。

Docker 客户端可以和守护进程运行在同一台机器上，也可以通过网络连接到远程的 Docker 守护进程。
### 3.3 Docker 守护进程(dockerd)
Docker 守护进程(dockerd)是 Docker 架构中的核心服务端组件，它负责：
- 接收来自客户端的请求；
- 管理容器的整个生命周期(创建、运行、停止、删除)；
- 管理镜像的拉取、构建和存储；
- 管理网络和数据卷。

dockerd 启动时会自动启动 containerd 子进程，二者通过 RPC 进行通信。
### 3.4 containerd
containerd 是一个容器管理系统，它从 Docker 中分离出来，专门负责容器的生命周期管理。

简单理解：dockerd 是“总经理”，负责接单和统筹；containerd 是“项目经理”，负责具体执行容器的创建和管理。

containerd 符合 OCI(Open Container Initiative)标准，这意味着它不仅服务于 Docker，也可以被 Kubernetes 等其他容器编排系统使用。

### 3.5 containerd-shim
containerd-shim 是 containerd 和 runc 之间的中间层。每启动一个容器，就会创建一个新的 containerd-shim 进程。

shim 的作用主要有两个：
- 解耦：将容器进程与 containerd 解耦。即使 containerd 本身升级或重启，已经运行的容器不会受到影响；
- 代理：作为容器进程的父进程，负责收集容器进程的状态，上报给 containerd。
### 3.6 runc
runc 是一个轻量级的容器运行时，它真正负责启动和控制容器。

runc 做的事情包括：
- 根据配置(如镜像的 rootfs、命名空间、cgroup 设置)准备好容器的运行环境；
- 调用 Linux 内核接口，创建命名空间、设置 cgroup；
- 启动容器进程。
runc 启动完容器后本身会直接退出，由 containerd-shim 接管容器进程的父进程角色。
### 3.7 完整工作流程
以执行 docker run nginx 为例，完整的调用链如下：
1. 用户在终端输入 docker run nginx，Docker 客户端将请求发送给 dockerd；
2. dockerd 检查本地是否有 nginx 镜像，如果没有则从仓库拉取；
3. dockerd 将创建容器的请求发给 containerd；
4. containerd 创建 containerd-shim 进程；
5. containerd-shim 调用 runc；
6. runc 利用 Linux 内核的命名空间和 cgroup 创建并启动容器进程；
7. runc 退出，containerd-shim 成为容器进程的父进程，持续监控容器状态。

## 四、镜像分层与存储原理
### 4.1 镜像概念
Docker 镜像是一个只读的模板，包含了运行应用程序所需的代码、运行时、库、环境变量和配置文件等一切内容。

镜像(Image)和容器(Container)的关系，就像面向对象编程中的类和实例—镜像是静态的定义，容器是镜像运行时的实体。
### 4.2 镜像分层
Docker 镜像由多个只读层组成，每一层都构建在前一层之上。用户在制作镜像时的每一步操作(如 RUN apt-get install、COPY 等)，都会生成一个新的层。

镜像分层的最大好处是共享资源：
- 多个镜像可以共享相同的基础层(如 Ubuntu、Alpine 基础镜像)，磁盘上只需保存一份；
- 内存中也只需加载一份基础层，就可以为所有基于该层的容器服务。
### 4.4 容器层与写时复制(CoW)
当容器启动时，Docker 会在所有只读镜像层的顶部添加一个可读写层，这一层被称为容器层。
- 镜像层：只读，不可修改；
- 容器层：可读写，所有对容器的改动(添加、删除、修改文件)都发生在这里。
当容器需要修改一个文件时，Docker 不会直接修改底层只读镜像中的文件，而是采用写时复制(Copy-on-Write，CoW) 策略：
- 将文件从只读的镜像层复制到可写的容器层；
- 在容器层中对这个副本进行修改。

这样做的好处是：
- 镜像保持不可变，多个容器可以共享同一份镜像数据；
- 每个容器只保存自己修改过的文件，节省磁盘空间；
- 容器删除时，只删除容器层的数据，不影响镜像。
### 4.4 存储驱动(Storage Driver)
Docker 使用存储驱动来实现 UnionFS 的分层存储。Rocky Linux 8(Linux 内核 4.0+)默认使用 OverlayFS 作为存储驱动。

OverlayFS 是 Linux 内核原生支持的联合文件系统，性能高、资源占用低。它将多个目录(层)叠加为一个逻辑文件系统，其中只读层(镜像)和读写层(容器)组合起来对外提供服务。

## 五、Docker 网络原理
### 5.1 网络命名空间
每个 Docker 容器都有自己的网络命名空间(Network Namespace) ，这意味着每个容器都拥有独立的网络栈—独立的网卡、IP 地址、路由表和端口空间。

这就解释了为什么可以在同一台宿主机上运行多个 Nginx 容器，而它们都监听 80 端口却不会冲突—因为每个容器在自己的网络命名空间里都有自己独立的 80 端口。
### 5.2 五种网络模式
1. Bridge 模式(默认)

Bridge 模式是 Docker 的默认网络模式。Docker 会在宿主机上创建一个虚拟网桥(通常名为 docker0)，每个容器通过一对 veth pair 连接到这个网桥上。
- 同一网桥上的容器可以通过 IP 地址相互通信；
- 容器通过宿主机的网卡与外部网络通信；
- 适合单机上多个容器之间的通信。

2. Host 模式

使用 Host 模式的容器共享宿主机的网络命名空间，没有独立的 IP 地址。
- 容器直接使用宿主机的网络栈，端口直接暴露在宿主机上；
- 不需要端口映射(-p 参数无效)；
- 性能最好，但隔离性最差；
- 适合对网络性能要求极高的场景。

3. None 模式

容器没有网络配置，完全隔离。合不需要网络通信的批处理任务。

4. Overlay 模式

Overlay 网络是跨主机的容器网络。它利用 VXLAN 技术将多个 Docker 主机的网络连接在一起，让不同主机上的容器可以相互通信。
- 适合 Docker Swarm 或 Kubernetes 集群；
- 用于构建分布式应用。

4. Macvlan 模式

Macvlan 让容器像网络上的物理设备一样运行，每个容器被分配独立的 MAC 地址。适合需要直接接入物理网络的场景，如网络流量监控。
### 5.3 常用网络命令
| 命令                                          | 说明               |
| ------------------------------------------- | ---------------- |
| docker network ls                           | 查看所有网络           |
| docker network create --driver bridge mynet | 创建自定义桥接网络        |
| docker run --network mynet nginx            | 在指定网络中运行容器       |
| docker network connect mynet 容器名            | 将已有容器接入网络        |
| docker network inspect mynet                | 查看网络详情(含所有连接的容器) |

**生产环境建议：** 在单机场景下，优先使用用户自定义的 Bridge 网络，而不是默认的 docker0 网桥。自定义网络提供内置的 DNS 解析，容器之间可以通过容器名直接通信，比用 IP 地址更稳定。

## 六、Docker 存储原理
### 6.1 容器存储的两种类型
容器的存储分为两类：
1. 容器层存储：容器运行时产生的临时数据，存储在容器层(可写层)，容器删除后数据丢失；
2. 持久化存储：需要长期保存的数据，通过数据卷或绑定挂载实现。
### 6.2 数据卷(Volume)
数据卷是 Docker 管理的存储空间，独立于容器的生命周期。
```bash
# 创建数据卷
docker volume create mydata

# 运行容器时挂载数据卷
docker run -d -v mydata:/app/data nginx

# 查看所有数据卷
docker volume ls

# 删除数据卷
docker volume rm mydata
```
数据卷的特点：
- 由 Docker 创建和管理，位于 /var/lib/docker/volumes/；
- 删除容器不会删除数据卷；
- 多个容器可以共享同一个数据卷；
- 适合生产环境的数据持久化。
### 6.3 绑定挂载(Bind Mount)
绑定挂载将宿主机的目录或文件挂载到容器内部。
```bash
docker run -d -v /host/data:/app/data nginx
```
- 容器对 `/app/data` 的读写会直接反映到宿主机的 `/host/data`；
- 适合开发环境(代码热更新)或共享配置文件；
- 生产环境使用需注意 SELinux 权限问题。

Rocky Linux 8 生产环境提示：如果挂载时遇到权限错误，可以在挂载参数后添加 :z：
```bash
docker run -d -v /host/data:/app/data:z nginx
```

## 七、容器生命周期
### 7.1 容器的状态
Docker 容器在其生命周期中会经历多种状态：

|状态|说明|
|---|---|
|Created|容器已创建，但尚未启动|
|Running|容器正在运行|
|Paused|容器中的进程被暂停(挂起)|
|Stopped|容器已停止(进程已退出)|
|Deleted|容器已被删除|
### 7.2 生命周期管理命令
|命令|说明|底层操作|
|---|---|---|
|docker create nginx|创建容器(不启动)|dockerd 准备容器配置，但未调用 runc 启动进程|
|docker start 容器名|启动已创建的容器|dockerd → containerd → shim → runc 启动进程|
|docker run nginx|创建并启动容器|相当于 create + start|
|docker pause 容器名|暂停容器进程|使用 cgroup freezer 挂起进程|
|docker unpause 容器名|恢复暂停的容器|解除 cgroup freezer|
|docker stop 容器名|停止容器(优雅)|发送 SIGTERM 信号，等待进程自行退出|
|docker kill 容器名|强制停止容器|发送 SIGKILL 信号，立即终止|
|docker rm 容器名|删除容器|删除容器层数据，释放资源|
### 7.3 生产环境最佳实践
1. 善用 --restart 策略：生产环境建议设置容器异常退出后的自动重启。
```bash
docker run -d --restart=unless-stopped --name web nginx
```
2. 合理设置资源限制：避免单个容器耗尽宿主机资源。
```bash
docker run -d --cpus=2 --memory=1024m --name web nginx
```
3. 数据持久化：生产环境务必使用数据卷(Volume)或绑定挂载，容器本身无状态。
4. 日志管理：容器日志默认存储在容器层，需配置日志轮转策略，避免磁盘占满。
```bash
docker run -d --log-opt max-size=10m --log-opt max-file=3 nginx
```

## 八、总结
Docker 的运行原理可以浓缩为以下几点：
1. 容器本质上是进程：容器不是虚拟机，而是受命名空间隔离和 cgroup 资源限制的普通进程。
2. 三大内核机制：命名空间(隔离)、cgroup(限流)、UnionFS(分层存储)是容器的三大基石。
3. 分层架构：从用户命令到容器运行，经过 CLI → dockerd → containerd → shim → runc 的调用链，各层职责分明。
4. 镜像分层 + 写时复制：镜像由多个只读层叠加而成，容器启动时添加可写层，修改文件时采用写时复制策略。
5. 网络隔离：每个容器拥有独立的网络命名空间，通过 Bridge、Host、Overlay 等网络模式实现不同场景的通信需求。
