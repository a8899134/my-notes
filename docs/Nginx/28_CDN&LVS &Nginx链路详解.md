## 一、整体架构概览
### 1.1 为什么需要多层架构
一个完整的 Web 服务入口通常由多层组成，每一层都有其不可替代的职责：

| 层级 | 组件 | 工作层级 | 核心职责 |
|------|------|----------|----------|
| 第一层 | DNS + GSLB | 应用层 | 域名解析、智能调度、就近接入 |
| 第二层 | CDN | 应用层(边缘) | 全球加速、静态缓存、DDoS 防护 |
| 第三层 | LVS + Keepalived | 传输层(四层) | 高可用流量分发、VIP 漂移 |
| 第四层 | Nginx | 应用层(七层) | URL 路由、限流、SSL 卸载、缓存 |

### 1.2 完整请求链路总览图
```
用户浏览器(北京)
    │
    │ ① 输入 https://www.example.com
    ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 第 1 层：DNS 解析                                                     │
│  - 本地 DNS 递归查询 www.example.com                                  │
│  - 权威 DNS 返回 CNAME：www.example.com.cdn.cloudflare.com            │
│  - GSLB 智能调度：根据用户 IP 选择最近的 CDN 节点                     │
└─────────────────────────────────────────────────────────────────────────┘
    │
    │ ② 请求到达 CDN 边缘节点(如北京 CDN 节点)
    ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 第 2 层：CDN 边缘节点                                                │
│  - 检查本地缓存                                                       │
│  - 静态资源(图片/CSS/JS/视频)→ 命中则直接返回                      │
│  - 动态请求(/api/)→ 缓存未命中，回源到源站                         │
└─────────────────────────────────────────────────────────────────────────┘
    │
    │ ③ 回源请求到达源站机房(如上海机房)
    ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 第 3 层：LVS + Keepalived(四层负载均衡 + 高可用)                  │
│  - 接收回源请求(目标 IP = VIP：192.168.1.100)                      │
│  - Keepalived 管理 VIP 漂移(主节点持有 VIP，备节点待命)            │
│  - LVS 根据调度算法(如轮询)选择一台健康的 Nginx                    │
│  - DR 模式：仅修改 MAC 地址，转发数据包                              │
└─────────────────────────────────────────────────────────────────────────┘
    │
    │ ④ 请求转发到选中的 Nginx(如 192.168.1.20)
    ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 第 4 层：Nginx(七层反向代理 + 业务网关)                           │
│  - 解析 HTTP 请求：域名(Host)、URL、Header、Cookie                 │
│  - 匹配 server_name → 对应站点配置                                   │
│  - 匹配 location → 决定如何处理                                      │
│  - 执行：反向代理、限流、缓存、SSL 卸载等                            │
└─────────────────────────────────────────────────────────────────────────┘
    │
    │ ⑤ 转发给后端应用服务器
    ▼
后端应用 → Redis → MySQL → 返回响应(原路返回)
```
### 1.3 一个通俗易懂的比喻
整套架构可以理解为一个高效的“物流配送系统”：

| 组件 | 角色 | 说明 |
|------|------|------|
| DNS | “导航地图” | 告诉用户去哪里取货 |
| CDN | “前置分仓(快递驿站)” | 把热门商品提前运到离用户最近的地方 |
| LVS + Keepalived | “总调度中心(双岗)” | 主调度官在岗，备用调度官待命，确保永不中断 |
| Nginx | “业务接待员” | 听懂用户需求后，引导到具体部门 |
| 应用服务器 | “业务部门” | 实际处理业务逻辑 |

## 二、第一层：DNS 解析与智能调度
### 2.1 DNS 解析过程
用户浏览器输入 `https://www.example.com` 后，发生的第一个关键步骤是 DNS 解析。

**接入 CDN 前后 DNS 的变化：**

| 接入阶段 | DNS 记录类型 | 指向 | 效果 |
|----------|-------------|------|------|
| 无 CDN | A 记录 | Nginx 服务器公网 IP | 用户直接访问源站 |
| 接入 CDN 后 | CNAME 记录 | CDN 服务商提供的域名 | 用户请求先经过 CDN 网络 |

```
DNS 解析结果示例：
www.example.com → CNAME → www.example.com.cdn.cloudflare.com
```
⚠️ **注意**：同一个主机记录(如 `www`)不能同时存在 A 记录和 CNAME 记录。接入 CDN 后，原来的 A 记录被替换为 CNAME 记录。

### 2.2 GSLB(全局负载均衡)智能调度
CDN 的 GSLB(Global Server Load Balancing)模块根据用户的地理位置、运营商和当前节点负载，返回最佳边缘节点 IP。

**调度依据：**

| 因素 | 说明 | 示例 |
|------|------|------|
| 地理位置 | 选择离用户最近的节点 | 北京用户 → 北京或天津节点 |
| 运营商 | 避免跨运营商延迟 | 电信用户 → 电信节点，联通用户 → 联通节点 |
| 节点负载 | 避开高负载节点 | 节点 A 负载 80%，节点 B 负载 40% → 选择 B |
| 链路质量 | 实时探测最低延迟路径 | 选择延迟最低的节点 |

## 三、第二层：CDN 边缘节点
### 3.1 请求到达 CDN 后的判断逻辑
CDN 边缘节点收到请求后，按照以下流程处理：
```
请求到达 CDN 边缘节点
    │
    ▼
判断请求内容类型
    │
    ├── 静态资源(图片、CSS、JS、视频、字体)
    │       │
    │       ▼
    │   检查本地缓存
    │       │
    │       ├── 缓存命中(HIT)→ 直接返回用户(源站无感知)
    │       │
    │       └── 缓存未命中(MISS)→ 回源到 LVS
    │
    └── 动态请求(/api/、/login/、.php 等)
            │
            ▼
        检查 CDN 缓存策略
            │
            ├── 配置了缓存(如 5 分钟)→ 检查缓存
            │
            └── 配置了不缓存 → 直接回源到 LVS
```
### 3.2 不同资源的处理方式

| 请求类型 | 示例 URL | CDN 处理方式 | 是否回源 |
|----------|----------|-------------|----------|
| 图片 | `/images/logo.png` | 缓存 30 天，命中则直接返回 | 首次请求或缓存过期后回源 |
| CSS/JS | `/static/app.js` | 缓存 1 年，带哈希的文件名 | 首次请求或文件名变化后回源 |
| HTML | `/index.html` | 缓存 1 小时 | 定期回源检查更新 |
| API | `/api/users` | 不缓存或缓存 1 分钟 | 几乎每次都回源 |
| 视频 | `/video/xxx.mp4` | 缓存 1 年 | 首次请求回源 |

### 3.3 CDN 回源配置
当 CDN 缓存未命中时，需要向源站回源。回源地址可以是 IP 或域名。

**推荐使用域名回源：**

| 方式 | 配置 | 优点 | 缺点 |
|------|------|------|------|
| IP 回源 | 填写 Nginx 公网 IP | 简单直接 | IP 变更需手动修改 CDN 配置 |
| 域名回源 | 填写 `origin.example.com` | IP 变更只需改 DNS，CDN 配置不变 | 需要多准备一个域名 |

在 CDN 控制台配置回源时必须保证回源 HOST 与 Nginx 的 server_name 完全一致：
```
# Nginx 配置
server {
    listen 80;
    server_name origin.example.com;   # ← 必须与 CDN 回源 HOST 一致
    # ...
}
```

## 四、第三层：LVS + Keepalived
### 4.1 LVS 的角色与原理
当 CDN 回源请求到达源站机房时，首先到达的是 LVS 服务器(持有 VIP)。

**LVS 看到的信息：**
- 目标 IP：`192.168.1.100`(VIP)
- 目标端口：`80` 或 `443`
- 协议：TCP

**LVS 看不到的信息：**
- ❌ 看不到域名(`Host` 头)
- ❌ 看不到 URL(`/api/users`)
- ❌ 看不到 Cookie、Header 等七层信息

LVS 的工作就是：根据 IP + 端口，选择一台健康的 Nginx，将数据包转发过去。
### 4.2 LVS 的工作模式(DR 模式)
生产环境最常用的是 **DR 模式**，因为性能最高。
```
客户端请求 → LVS(仅修改目标 MAC 地址)→ Real Server(Nginx)
                                                    │
                                                    ▼
                                          响应直接返回客户端(不经过 LVS)
```

**DR 模式的核心特点：**

| 特点 | 说明 |
|------|------|
| LVS 只处理入站流量(请求) | 出站流量(响应)由 Real Server 直接返回，LVS 压力极小 |
| 性能极高 | 单台 LVS 可支撑百万级并发连接 |
| 要求同网段 | LVS 和 Real Server 必须在同一个物理网段 |
| Real Server 需要绑定 VIP | 在 lo 接口上绑定 VIP，并抑制 ARP 响应 |

**Real Server 配置示例：**
```
# 在 lo 接口绑定 VIP
ip addr add 192.168.1.100/32 dev lo:0

# 抑制 ARP 响应(避免 VIP 冲突)
echo 1 > /proc/sys/net/ipv4/conf/lo/arp_ignore
echo 2 > /proc/sys/net/ipv4/conf/lo/arp_announce
```
### 4.3 Keepalived 的高可用机制
LVS 本身是单点故障。Keepalived 基于 VRRP 协议 为 LVS 提供高可用。
```
        ┌─────────────────────────────────────┐
        │           VIP：192.168.1.100        │  ← 对外统一入口
        └─────────────────────────────────────┘
                         │
        ┌────────────────┴────────────────┐
        ▼                                 ▼
┌───────────────────┐           ┌───────────────────┐
│   LVS Master      │───心跳───▶│   LVS Backup      │
│   优先级: 100     │  (VRRP)   │   优先级: 90      │
│   持有 VIP        │◀──────────│   待命            │
└───────────────────┘           └───────────────────┘
```
**故障切换流程：**

| 步骤 | 说明 | 耗时 |
|------|------|------|
| 1 | Master 定期通过 VRRP 心跳向 Backup 报告状态 | 每秒 1 次 |
| 2 | Backup 检测到 Master 心跳超时 | 约 1-3 秒 |
| 3 | Backup 自动接管 VIP(VIP 漂移) | 瞬间完成 |
| 4 | Backup 开始处理客户端请求 | 秒级切换完成 |

### 4.4 LVS 调度算法
LVS 支持多种调度算法，常用的是：

| 算法 | 说明 | 适用场景 |
|------|------|----------|
| `rr`(轮询) | 按顺序轮流分配 | 后端 Nginx 性能一致时 |
| `wlc`(加权最少连接) | 根据权重和连接数动态分配 | 后端性能不一致时 |
| `wrr`(加权轮询) | 按权重比例分配 | 简单场景 |

## 五、第四层：Nginx
### 5.1 Nginx 的角色与原理
请求到达 Nginx(Real Server)后，Nginx 开始工作在 七层(应用层)。

**Nginx 看到的信息：**
```
GET /api/users HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0
Cookie: session_id=abc123
X-Real-IP: 223.104.x.x
```

**Nginx 的决策流程：**
```
收到请求
    │
    ▼
① 根据 Host 头匹配 server_name
    │ → 找到对应的站点配置
    ▼
② 根据请求 URI 匹配 location
    │ → 确定处理方式
    ▼
③ 执行 location 块中的指令
    │ → root / proxy_pass / limit_req / ...
    ▼
④ 返回响应或转发给后端
```
### 5.2 Nginx 与 LVS 的协同配置
当 Nginx 部署在 LVS 后方时，需要注意以下配置：

#### 配置一：确保 server_name 与回源 HOST 匹配
```
server {
    listen 80;
    server_name origin.example.com;   # 与 CDN 回源 HOST 一致
    # 或包含业务域名
    server_name example.com www.example.com;
}
```

#### 配置二：获取客户端真实 IP

接入 CDN 后，Nginx 的访问日志默认记录的是 CDN 节点的 IP，而不是用户的真实 IP。需要配置 real_ip 模块：
```
http {
    # 信任 CDN 节点的 IP(生产环境应替换为具体的 CDN IP 段)
    set_real_ip_from 0.0.0.0/0;
    real_ip_header X-Forwarded-For;
    real_ip_recursive on;
}
```

#### 配置三：透传客户端信息给后端应用
```
location /api/ {
    proxy_pass http://backend;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```
### 5.3 Nginx 的精细化处理能力
Nginx 在七层可以做很多 LVS 无法做到的事情：

| 功能 | 配置示例 | 说明 |
|------|----------|------|
| URL 路由 | `location /api/ { proxy_pass ... }` | 根据路径转发到不同后端 |
| 限流 | `limit_req zone=api_limit burst=20;` | 防止 CC 攻击 |
| SSL 卸载 | `listen 443 ssl;` | HTTPS 加密解密 |
| 静态缓存 | `expires 30d;` | 设置浏览器缓存 |
| 重写 | `rewrite ^/old/(.*)$ /new/$1;` | URL 重写 |

## 六、完整请求链路追踪(实战示例)
### 6.1 完整的链路追踪
以一个北京用户访问 `https://www.example.com/api/users` 为例：

| 步骤 | 处理层 | 具体动作 | 数据变化 |
|------|--------|----------|----------|
| **①** | 用户浏览器 | 输入 `https://www.example.com/api/users` | - |
| **②** | DNS 解析 | 返回 CNAME 指向 CDN 域名 | `www.example.com` → `cdn.example.com` |
| **③** | GSLB 调度 | 选择北京 CDN 节点 IP | 返回 `103.x.x.x` |
| **④** | CDN 边缘节点 | 检查缓存，未命中 → 回源 | 转发到源站 VIP `192.168.1.100:443` |
| **⑤** | LVS Master | 接收请求，选择一台健康 Nginx | 转发到 Nginx-2 `192.168.1.20:443` |
| **⑥** | Nginx-2 | 解析 Host/URL，执行 `proxy_pass` | 转发给后端应用 `10.0.1.10:8080` |
| **⑦** | 后端应用 | 处理业务逻辑，查询数据库 | 返回 JSON 数据 |
| **⑧** | Nginx-2 | 接收响应，返回给用户 | 通过 LVS? **不**，DR 模式直接返回给 CDN |
| **⑨** | CDN 边缘节点 | 缓存响应(如配置了缓存) | 返回给用户 |
| **⑩** | 用户浏览器 | 显示结果 | - |

### 6.2 各层之间的协同要点

| 连接点 | 关键配置 | 说明 |
|--------|----------|------|
| CDN → LVS | CDN 回源地址指向 LVS 的 VIP | LVS 的 VIP 是源站的唯一入口 |
| LVS → Nginx | LVS 的 Real Server 列表包含所有 Nginx IP | 健康检查自动剔除故障 Nginx |
| Nginx → 应用 | `proxy_pass` 指向应用服务器 | 七层精细化路由 |

### 6.3 技术选择参考

| 场景 | 注册用户 | 日活(DAU) | 日 PV | 峰值并发 | 是否需要 LVS？ |
|------|----------|-----------|-------|----------|----------------|
| 个人博客 | < 1 万 | < 1000 | < 1 万 | < 10 | ❌ 不需要 |
| 小型企业官网 | 1 万-10 万 | 1000-5000 | 1 万-10 万 | < 100 | ❌ 不需要 |
| 中型电商/资讯站 | 10 万-100 万 | 1 万-10 万 | 10 万-100 万 | 100-500 | ❌ Nginx 足够 |
| 区域门户/垂直平台 | 100 万-500 万 | 10 万-50 万 | 100 万-500 万 | 500-3000 | 🟡 Nginx 集群基本够用，可开始关注 LVS |
| 全国性媒体/电商 | 500 万-1000 万 | 50 万-100 万 | 1000 万+ | 3000-1 万 | ✅ 强烈建议引入 LVS |
| 头部大厂 | 1 亿+ | 1000 万+ | 数亿 | 10 万+ | ✅ LVS + 自研网关 |

**总结**：用户请求从浏览器发出到最终到达后端应用，经历了一条精心设计的链路—DNS 负责“指路”，CDN 负责“就近”，LVS 负责“分发”，Nginx 负责“路由”，每一层各司其职，共同构成高可用、高性能的 Web 服务入口。
